# Onsite Ticket UI Implementation Plan

## Design

**Goal:** 旅行中に「いまの予定」「次の予定」と進行・再計画の操作を見つけやすくし、旅行前・候補比較と紙の切符の世界観を揃える。

共有HTMLの07パターンAを参考に、既存CurrentCard/NextCard/Routeを活かす。全面的なルート組み直しや半券ドラッグによる進行は、誤操作・状態管理が増えるため今回行わない。ユーザーの「UI改善お願いします」を受けた次段階である。

- いまの予定は大きい予定時刻・名前、紙面・控えめな破線の切符風カードにする。番号等の装飾は予約・購入・発券を示さない。
- 次の予定は時刻・名前・固定・移動の根拠が読み取れる簡潔な案内にする。確認不能・矛盾・重なる予定の説明、Google帰属を隠さない。
- 手動更新であることを上部に明示し、進行位置を予定番号/全予定数で伝える。GPS・現在時刻・訪問実測として表示しない。
- 「進む」「戻す」「この予定だけ変更」の既存操作を、いま/次の案内の直後・全路線より前へ置く。最後の予定の振り返り導線と利用不可理由を維持する。
- 全路線は補助的な一覧として続ける。手動の進行位置、順番、固定、番号を保ち、模式図であることを説明する。
- 320px/390pxで文字・注意・操作が見切れず、色だけで状態を伝えない。装飾はクリック・フォーカス・帰属表示を妨げない。

## Architecture and constraints

既存TripProgressViewの表示順と部品の見た目だけを変更する。progress-model・進行state・Trip切替・onReplan/onFinishの意味・API・認証・保存・本番設定を変更しない。新しい画像・依存・外部API呼出し・位置情報取得は不要。

基点origin/main 940024e。#88の最新HEAD承認・CI成功・未解決コメントなしを確認しSquash統合済み。feat/onsite-ticket-ui上で作業し、PR作成・CI確認・レビュー依頼まで。マージしない。
