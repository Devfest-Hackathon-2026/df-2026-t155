# GroundTrip：UI/UXの実装原則（暫定）

> **確定済みの画面仕様ではない**。最新版のチーム判断・承認済みデザイン（Figma等）が優先する。ただし、変更範囲の明示・固定予定の保護・根拠の正確な表現・本人承認というプロダクトの原則を守る。

## ユーザーが達成すること

- **「ここだけ直したい」を根拠を見ながら実現する。** AIの提案を受け入れるかは利用者が決める（Own the Why）。旅行計画の便利さとAIを鵜呑みにしない判断を、同じ操作にする。
- 入口は軽くする。旅行先・日付・希望から早く旅程作成に進めるようにし、追加条件は必要時に提示する。初回ログイン必須／ゲスト利用の可否は**未決定**。
- 旅行前は旅程全体（時刻順の予定・移動・固定予定）と重大な未確認事項を把握できるようにする。旅行中は**次の予定・時刻・固定予約・再計画の操作**を優先し、長文入力を強いない。
- 旅行前の部分修正と、旅行中の閉店・遅延等のトラブル対応は、可能な限り**同じ修正フロー／ドメイン処理**を使用する。「報告」だけで行き止まりにしない。
- 振り返りでは「情報源・AI提案・現地状況の食い違い」と「利用者の好み・移動負担等の経験」を区別する。本人が**編集・承認した学びだけ**保存し、次回どこへ反映したか分かるようにする。

## UIが守る状態と不変条件

1. **対象を特定**：変更するStop IDと範囲、固定予定が明確。ロックを勝手に解除しない。
2. **承認前に差分**：候補ごとに変更内容、時刻・移動・費用等の影響（根拠があるもののみ）、保持される予定、未確認事項を示す。**承認前は元の旅程を維持**する。
3. **根拠の正確さ**：`情報源と整合`／`矛盾あり`／`確認できない`を区別。情報源・照合時刻・対象日時/適用範囲を示し、「整合」を現実の正しさの保証にしない。**施設の存在／対象日時の営業／ユーザーが読んだこと**を同一の「確認済み」にしない。
4. **失敗を安全に表示**：有効候補なし・情報不足・API失敗・生成中・通信中断を区別する。固定条件を無断で緩めない。再試行や条件の見直しを案内し、元の旅程を保持する。
5. **重要度とアクセシビリティ**：固定予約・時間制約・重要な未確認事項を意図的に隠さない。状態を**色だけで伝えない**。スマートフォン片手操作や小画面での主要CTAの到達可能性を考慮する。

## 画面設計の扱い（未確定）

- 資料の **S1〜S5**（旅の作成／旅程一覧・確認／部分修正・比較／現地／振り返り・次回）は**情報領域・ユーザーフローの例**であり、5画面・5タブの指定ではない。画面統合、ナビゲーション、コンポーネント分割はデザイン決定に従う。
- 旅雑誌型／交通・実用型／両立型は**比較候補**。青＋白、カード、写真、角丸、書体、AIキャラクター、レベル制度などを勝手に正式仕様にしない。
- 資料中の京都・清水寺・昼食・14:00の予約、移動時間や料金は**画面／デモ用の例示**。実データや確定した要件として扱わない。
- 390px前後を設計起点とする案はあるが、厳密な幅やブレークポイントは未決定。選ばれたデザインと実際の端末で確認する。
- UIを実装・変更するときは、**確定したデザインの有無を確認**し、未確定の点は既存コンポーネントやプロダクト原則に沿う最小限の判断に留める。デザイン担当の承認なしに独自の全面的なビジュアル方針を導入しない。

## 実装・レビューでの確認

該当する変更では、スマホ表示、状態の区別、重要情報の視認性、変更対象と固定予定、承認前後の差分、失敗時の元データ保持を確認する。実施していない確認はPRで未実施と明記する。
