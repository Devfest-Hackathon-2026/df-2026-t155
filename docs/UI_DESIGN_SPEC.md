# GroundTrip UIデザイン仕様

## 1. 目的と適用範囲

GroundTripの旅程作成・確認・部分修正・現地対応・振り返り・次回反映に共通する**MVPのUI設計仕様**を定める。画面の見た目だけでなく、状態の意味、操作の結果、利用者に伝える情報を統一する。

中心となる体験は **「AIの提案を、人間が根拠で選ぶ（Own the Why）」**。利用者に確認作業を強制するのではなく、旅行計画を便利にする操作の中で、提案・根拠・制約・自分の判断を自然に区別できるようにする。

- 本書は**採用するUI設計**を示すものであり、開発進捗・ブランチ・PRの記録ではない。
- プロダクトの不変条件は`docs/PRODUCT_AND_ARCHITECTURE.md`、利用者保護の詳細原則は`docs/UX_DESIGN_PRINCIPLES.md`、データ型・APIの意味は`docs/DOMAIN_CONTRACTS.md`に従う。
- UIの表示方法は本書で統一するが、存在しないデータ、未対応のAPI、予約状態、成功した保存などを見た目のために補完しない。
- S1〜S5の情報領域を機械的に5タブへ分ける必要はない。画面遷移と部品の分割は、利用者が迷わず操作できることを優先する。

## 2. 全体のビジュアルとレイアウト

### 基本スタイル

- **明色テーマ**を基本とする。ページ外側もGroundTripの画面の一部であり、OSのダークモードによって一部分だけ黒い背景へ切り替えない。
- オフホワイトの背景、白いカード、濃い文字、オレンジのアクセントを基調とする。コンテンツ全体を必要以上に大きなカードで囲わず、意味のある予定・比較・通知単位を区別する。
- 予定の種類、承認状態、根拠、制約、固定を**色だけ**で区別しない。文字・形・アイコンも併用する。
- 状態の役割を統一する。**青は比較中の未承認候補、グレーは元の経路・補助線、オレンジは適用済み／進行中に注目する経路**を基本とする。根拠の整合等に使う色と、本人の承認を表す色を混同しない。
- 大きな見出し、カード内の情報階層、余白、角丸、タップ領域を揃える。装飾よりも時刻・場所・根拠・次の操作を優先する。

### レスポンシブ設計

- **スマートフォン縦画面を第一の設計対象**とし、片手でも主要操作に到達できるようにする。
- 320px・390px前後の狭い画面でも、重要な注意・固定予定・承認操作が隠れず、横スクロールを要求しない。
- PCではコンテンツの横幅を適切に制限する。スマートフォン用のカードを画面いっぱいに引き伸ばさない。

## 3. 路線図と予定カード

### 路線図

- 旅程一覧の主軸は**縦型路線図**。予定を時刻順の駅としてつなぎ、移動区間を駅間に配置する。
- 路線図は**訪問順を示す模式図**であり、地理的な縮尺・位置関係を正確に再現する地図ではない。その旨を必要な箇所で説明する。
- 各予定の名前、順序、予定時刻、推定滞在時間、必要な注意と固定状態を読み取れるようにする。
- 移動区間は、手段・所要時間と、その値が照合済みか不明かを明示する。所要時間が不明なら0分やAIによる推定値で埋めない。

### 駅とチケットの使い分け

- 観光・散策などの通常の予定は**駅ノード**で表示する。
- 食事・カフェなどは、路線図につながる**フードチケット風カード**で表示できる。すべての予定をチケット化しない。
- 旅行前の予定カードには、番号付き半券や紙面の意匠を補助的に使える。これは順序を伝える表示であり、乗車券・予約・購入を示さない。食事などの色分けは実際の予定種別に限る。
- **固定状態は予定の種類とは独立**している。駅やチケットの種類を変更せず、ロックアイコンと「固定予定」表示を重ねる。
- 「固定」「要予約」は「予約済み」「購入済み」を意味しない。根拠がない予約完了・発券完了表示やQRコードを設けない。
- 独立した乗車・乗換などの予定と、予定間の単なる移動区間を混同しない。UI上の種別は共通データ契約に従い、未指定の種別は「予定」と表示する。

## 4. 旅程の作成と確認

- 旅行先・日付・希望条件から、できるだけ少ない操作で旅程生成へ進める。必須の入力と追加条件を区別する。
- Geminiが作成した内容は**提案**として提示する。AIによる生成だけで、外部情報と照合済み・本人承認済み・保存済みと表示しない。
- 旅行前には旅程全体の順序、時刻、移動、固定した予定、重大な未確認事項を見やすくする。
- 予定の詳細では、根拠・対象日時・照合日時・説明・移動情報などを確認でき、変更可能な予定から部分修正へ進める。
- 固定の切り替えは本人の明示操作とし、固定された予定は本人が解除しない限り部分修正の対象にしない。
- データが不足している場合は不足を示し、現実には確認できていない営業時間や料金を補わない。

## 5. 根拠・制約・承認の表示

以下の状態は異なる軸として管理し、UIでも混同しない。

- **根拠の照合：** `consistent`（情報源と整合）、`conflicting`（矛盾あり）、`unverifiable`（確認できない）
- **未照合：** `evidence: []`。照合して確認できなかった状態と区別し「未照合」と表示する
- **制約判定：** `not_checked`（未検証）、`satisfied`（条件を満たす）、`violated`（条件違反）、`unknown`（判断できない）
- **本人の判断：** `pending`（判断前）、`approved`（承認）、`rejected`（却下）
- **固定：** `Stop.isFixed`。承認・予約・購入の状態とは独立する

表示する際は次を守る。

- 「情報源と整合」は現実世界で必ず正しいことの保証ではない。**施設の存在、対象日時の営業、移動時間**を別々に扱う。
- 出典・照合日時・対象日時・適用範囲を確認できるようにする。推測値やモック値を照合済みの値と同じ表示にしない。
- 利用者に「予定に収まる」などの平易な表現を用いる場合も、何を検証した結果なのか分かるようにする。根拠が不足する場合に「間に合う見込み」と断定しない。
- 条件違反・未検証・判断不能の候補を、承認できる案として提示しない。理由と次の操作を説明する。
- 候補がない、情報が足りない、通信・APIが失敗した、処理中である、を区別する。

## 6. 1地点の部分修正・候補比較

### 変更の範囲

- 利用者が変更対象の**1地点**と理由を指定する。他の予定と固定予定は維持する。
- 未承認の候補は元の旅程を書き換えない。候補を選ぶ操作と、正式に承認・適用する操作を分ける。
- 複数候補の間で選択中の案が明確であり、選択内容と路線図の分岐、差分表示が連動する。

### 比較画面

- **候補切り替えを路線図の直前に配置**し、選択中の分岐を青、元の経路をグレーで示す。適用後の状態は未承認の色と区別する。
- 元の予定と候補を比較し、変更前後の予定、隣接する移動区間、後続の固定予定への影響を示す。
- 移動時間の数値差は、手段・出典の性質・取得条件が比較可能な値からのみ算出する。比較できなければ「未確認」と表示する。
- 費用や味など、データのない属性で順位づけしない。利用者の希望と検証済みの比較軸は別に扱う。
- 不成立・未確認の候補、取得失敗、キャンセルによって元の旅程を破壊しない。
- 正式な適用では、サーバー側で所有者・旅程の版・変更前の予定・固定条件・制約を改めて確認する。画面に表示した検証結果のみを信頼しない。

## 7. ボトムシートと操作フィードバック

### 詳細ボトムシート

- 予定を選択した際は、画面下部から**詳細ボトムシート**を開く。
- 旅行前の路線図・詳細は生成りの紙面や控えめな破線で一貫させ、予定名・時刻・根拠・固定状態の可読性を優先する。
- ハンドルはドラッグ可能であることを表す。**下方向ドラッグ、背景タップ、明示的な閉じるボタン、Esc**で閉じられるようにする。
- 閾値に達しない短いドラッグや操作の中断では元に戻す。シート内部のスクロールやボタン操作を妨げない。
- **モーダルとして動作**させ、開いている間は背景をポインター・キーボード・支援技術から操作不可にする。`Tab`と`Shift+Tab`の移動はシート内に留める。
- 開いた際は適切な位置へフォーカスし、閉じた後は原則として起点の予定へフォーカスを戻す。親の旅程更新や非同期処理でも不正なフォーカス移動を起こさない。

### アニメーションと通知

- シート開閉、入力から比較への移行、候補の切り替え、処理中・失敗の変化に**意味のある短い遷移**を使う。移動が遅く感じられる演出や、誤操作を生む連続アニメーションは避ける。
- `prefers-reduced-motion`を尊重する。アニメーションなしでも状態変化が伝わるようにする。
- キャンセル・成功・エラー通知は、背景・文字・枠線に十分なコントラストを確保し、文言でも結果を表す。
- 通知が自動読み上げされる場合は、適切なライブリージョンを維持し、**テキスト内容の更新**として通知する。`role="status"`と`role="alert"`の用途を区別する。
- 入力フォームは**空欄かつ非フォーカスでも編集領域が明確**であること。入力枠など必要な視覚的境界は、隣接色に対して3:1以上のコントラストを確保する。

## 8. 現地対応・振り返り・次回への反映

- 旅行中は全旅程の概要より**現在・次の予定、時間制約、部分修正・再計画の入口**を優先する。
- 旅行中の進捗・現在地・到着は、実際に取得した情報と本人の報告を区別する。時刻や模擬イベントからGPS追跡したように見せない。
- 閉店・遅延などの現地トラブルには、旅行前と同じ変更対象・候補比較・承認の考え方を適用する。
- 振り返りでは、情報源・AI提案・実際の体験の食い違いと、本人の好み・移動負担を区別する。
- 学びを次回に反映する場合は、**本人による編集・承認を必要**とし、次回どの条件に反映されたかを示す。基盤モデルが再学習したとは表現しない。

## 9. 外部データ・デモの扱い

- Google Places／Routes由来のデータを路線図などに表示する場合は、適用されるGoogle Maps Platformの帰属表示・利用条件を守る。詳細は`docs/API_CONNECTIVITY_FINDINGS.md`を参照する。
- 地点・経路・営業時間・費用について、実データ、推定、未照合、モックを視覚的・文言的に区別する。
- 交通手段・料金・予約状況などの値を取得できない場合は**不明または未対応**として扱う。対応していない交通手段の時刻を照合済みと表示しない。
- 実際の位置情報を利用する場合は、目的と取得する情報を説明し、必要な同意を得る。常時位置追跡を前提にしない。

## 10. MVPの基本設計に含めない拡張表現

次の項目は、上記のUIを実装するための必須条件にしない。

- 新幹線・特急等を表す乗車券風の装飾
- チケットを物理的に「切る」演出、完了実績時刻の追加と取り消しの仕組み
- 予約済み・購入済みを証明する独立した予約管理機能
- 裏付けのない価格・味ランキングや、AIキャラクター・レベル制度

これらを追加する際は、必要なデータ契約と利用者への説明を別途定める。既に採用した路線図・部分修正・根拠表示の原則は維持する。
