# MVP共通データモデル・入出力契約（初期実装）

Issue #4の並行開発用の共有契約。日帰り・1地域・3〜4地点・1地点の部分修正を対象とする。
API接続・永続化・認可・画面・制約検証エンジンは含まない。最終的なAPI・DB設計ではない。

## 利用方法

フロントエンド・サーバーともに`@/domain`からスキーマと`z.infer`由来の型を利用する。
React、Next.js、外部サービスSDKには依存しない。境界では型アサーションで済ませず、
入力・LLM出力・サービスから組み立てた応答に`parse`または`safeParse`を使う。

```ts
import { GenerateTripRequestSchema, type Trip } from '@/domain'

const result = GenerateTripRequestSchema.safeParse(input)
// result.successを確認してからresult.dataを使用する。
```

スキーマは未知のキーと暗黙の型変換を拒否する。文字列の前後の空白は除去する。
外部APIの生レスポンスをそのまま渡さず、アダプターで共有モデルに変換する。
`src/domain/samples.ts`に架空の3地点旅程・生成入力・現地模擬報告からの修正候補・
振り返りの学び候補・過去の承認済み学びを用意した。実在施設・営業時間・移動時間を表さない。

## モデルと責務

| モデル     | 主な内容・意味                                                                             |
| ---------- | ------------------------------------------------------------------------------------------ |
| `Trip`     | ID、版、日付、地域、タイムゾーン、希望、3〜4件のStop、学びの適用先と説明                   |
| `Stop`     | 安定ID、表示名、Place IDまたは未同定の`null`、予定開始時刻、滞在分数、固定状態、根拠       |
| `Evidence` | 照合対象、主張、対象日時・適用範囲、出典、照合日時、3状態、説明                            |
| `Revision` | 対象Trip/版/Stop ID、理由、旅行前／現地の文脈、1件の前後差分、影響説明、制約検証、本人承認 |
| `Learning` | 元Trip ID、情報検証／個人の好みの区別、本人が編集する内容、適用範囲、本人承認              |

### 根拠・制約検証・本人承認を分ける

`Evidence.status`は`consistent`（情報源と整合）、`conflicting`（矛盾あり）、
`unverifiable`（確認できない）。表示文言は`evidenceStatusLabels`に定義する。
整合は現実の正しさ・将来の営業の保証ではない。施設同定と営業時間等は`subject`で分ける。
情報不足や取得失敗では、照合を試みた日時を`checkedAt`、理由を`explanation`に記録する。
まだ照合自体を行っていない場合は根拠を捏造せず、`evidence: []`とする。

出典はPlaces／Routes／公式情報／本人の現地報告／模擬情報を区別する。
Geminiの説明自体を検証済み根拠にしない。`user_report`も客観的事実の保証ではない。
出典URLは存在する場合だけHTTP(S) URLを設定する。

`Revision.constraintCheck`は決定論的制約検証の結果であり、根拠の整合状態とは独立する。
`not_checked`／`satisfied`／`violated`／`unknown`を区別する。
未検証を既定の成立扱いにせず、`satisfied`以外の承認済みRevisionは拒否する。
この初期実装は判定エンジンを実装せず、宣言された状態と形の矛盾だけを検証する。

承認は`pending`／`approved`／`rejected`。承認・却下にはタイムゾーン付きの決定日時が必要。
承認状態の申告を認可の証拠にはできない。サーバー側の本人確認と状態遷移が別途必要。

### 部分修正と元旅程の保護

`Revision.diff.before/after`は対象1件のみ。前後でStop IDを維持し、施設を変えてもIDは変えない。
固定は場所・時刻・滞在時間を含むStop全体の固定として扱い、固定Stopへの修正・固定解除は拒否する。
ロック操作そのものは別機能とし、この契約に混ぜない。

提案応答には未承認のRevisionだけを含め、更新後のTripを含めない。
元旅程と候補を別に保持し、利用者が比較して承認するまで反映しない。
承認済みRevisionも「適用済み」を意味しない。今回、旅程を書き換える関数は実装していない。

適用処理の実装時には、サーバーで本人の権限・最新の`Trip.version`・対象ID・
`diff.before`と現在のStopの一致を確認し、移動・時刻・固定条件を再検証する。
対象以外を保持した更新と版の加算を一体として行う。クライアントからのTripや
`constraintCheck: satisfied`を信用して直接保存してはいけない。
現在のスキーマ単独では、別々に検証した要求と応答の対応関係や実行可能性までは保証しない。

旅行前は`context.phase: planning`、現地は`on_site`とし、同じ修正契約を使う。
現地の`report.kind`は`actual`／`simulated`を必須にし、模擬トラブルを実測情報と混同しない。

### 振り返りと次回への反映

`Learning`は本人の編集・承認前の候補を表せる。承認済み内容を編集した場合、
アプリケーション層で再び`pending`に戻して再承認を求める必要がある。
適用範囲は暫定的に全地域／指定1地域。地域は生成入力と完全一致で照合する。

生成入力の`learnings`は承認済みだけを許可し、却下・未承認・地域不一致を拒否する。
実APIではサーバーが本人の承認済みレコードを取り出し、クライアントの自己申告を信用しない。
生成したTripの`learningApplications`は学びID・対象Stop ID・説明を保持し、
前回のどの学びを今回どこに反映したかを示す。対象Stopの存在とID重複を検証する。
入力の承認済み学びとの対応、説明の正確さは生成処理側で検証する必要がある。
基盤モデルの再学習ではない。現地対応・振り返り・次回反映はいずれもMVP必須機能である。

## 主要入出力

| 操作     | リクエスト                                                                    | レスポンス                                         |
| -------- | ----------------------------------------------------------------------------- | -------------------------------------------------- |
| 旅程生成 | `GenerateTripRequest`：日付・地域・タイムゾーン・希望・固定Stop・承認済み学び | `status: proposed`とTrip、または失敗               |
| 部分修正 | `ReviseTripRequest`：現在のTripのスナップショット・対象Stop ID・理由・文脈    | `status: proposed`と未承認Revision配列、または失敗 |

部分修正の候補配列は同じTrip・版・対象Stopに限定する。
失敗は`no_candidates`（成立候補なし）、`insufficient_information`（情報不足）、
`external_service_error`（外部サービス失敗）と説明文を持ち、更新旅程を含めない。
通信中断・送信中・生成中はクライアントの操作状態として扱い、完了応答の状態と分ける。
生成のTripも提案段階。`proposed`を自動保存・自動採用の指示と解釈しない。

## 今回の仮定と未決定事項

- 日付はISO日付、予定時刻は旅程のタイムゾーンでの`HH:mm`、照合・決定日時はオフセット付きISO日時。
  `timeZone`はIANAタイムゾーン識別子（`Asia/Tokyo`、`UTC`、`Etc/GMT+9`等）とし、`+09:00`等の固定オフセットは拒否する。
  滞在は当日内に収める。海外の夏時間や日跨ぎ旅程は対象外。停止順は配列順で表す。
- 地域は単一の文字列。地域コード・範囲判定・表記揺れの正規化は未決定。Place IDは未同定の`null`を許容する。
- `version`は0以上の整数。将来の同時編集・古い候補の適用防止に使うが、永続化方式は未決定。
- 固定はStop全体、修正は1件置換のみ。前後Stopの時刻変更が必要な場合は自動で範囲を広げず、
  成立候補なし／情報不足として返す。対象外の時刻変更を許すかは別途合意する。
- 影響は根拠のある説明文と前後のStopで示す。移動区間モデル、経路・費用の構造化差分、
  制約違反の詳細形式は未決定。サンプルには根拠のない所要時間・料金を設定しない。
- 生成で渡した固定予定の保持、学びの適用先、要求と応答の一致を検証する処理は、
  今後の生成・修正処理で実装する。Zodの構造検証だけでこれらの保証は成立しない。
- API URL・HTTPステータス・認証・永続化DTO・承認／適用API・学び編集／保存APIは未決定。
  部分修正入力は初期連携用のTripスナップショットであり、サーバーの正本ではない。
- Google Maps情報の保存期間・表示上の帰属・再照会方針は外部アダプター実装前に確認する。
  このモデルの存在は、施設情報の無期限保存の許可を意味しない。

これらの未決定部分は後続機能の作業項目であり、現地対応・振り返り・次回反映を任意機能にするものではない。
