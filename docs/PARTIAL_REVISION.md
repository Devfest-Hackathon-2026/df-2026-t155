# 部分修正（Issue #9）の候補生成と制約検証：責務の境界とAPI

Issue #9（1地点の部分修正）のうち、**代替候補の生成・照合・制約検証・未承認Revisionの返却**まで。
本人承認後の適用は[保存済みRevisionの適用契約](FIRESTORE_PERSISTENCE.md#revisionの適用と再取得)を参照。
#11（現地報告からの再計画）も、**同じ処理**を使う（`context`で、旅行前と現地報告を区別する）。

## 責務の分担

| 担当                         | 責務                                                                                                                                                           |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 候補の生成・検証（この文書） | 代替候補（最大3件）をGeminiで作る → Placesで施設を特定・営業時間を確認 → Routesで前後の移動と固定予定への影響を検証 → 未承認のRevisionと、移動区間の比較を返す |
| 比較UI・承認・適用           | 候補の比較表示、本人の承認、旅程への適用。**適用の直前に、サーバー側で認可・版・制約を再検証する**                                                             |

候補の生成側は、**元のTripを更新しない**。保存もしない。返すのは、未承認（`pending`）のRevisionと、一時的な比較データだけ。

## API：POST /api/trips/revise

共通契約（`src/domain/contracts.ts`）の`ReviseTripRequest`／`ReviseTripResponse`を使う。

- リクエスト：`{ trip, targetStopId, reason, context, travelModes? }`。
  - `context`は`{ phase: 'planning' }`か、`{ phase: 'on_site', report: { kind, description, category, targetStopId } }`。
    `kind`は`actual`／`simulated`、`category`は`closed`／`crowded`／`delayed`／`other`。報告対象は修正対象と一致させる。
    `kind`と`description`だけの旧形式は引き続き読める。候補への影響は未確認として扱う。
  - 対象は、存在し、固定されていない予定だけ（契約で検証）。
  - `travelModes`（任意）：利用者が使える移動手段（`walk`／`drive`）。**省略時は徒歩だけ**（下の「移動手段」）。
- 成功：HTTP 200、`{ status: 'proposed', revisions, comparisons?, proposalTokens? }`。`revisions`は1〜3件で、**すべて`pending`**。同じ旅程・版・対象。
- 失敗（元の旅程は維持される）：`no_candidates`／`insufficient_information`は422、`external_service_error`は502。
  API層のエラーは、旅程生成APIと同じ（400／413／415／500／503）。
- 署名付き候補を保存できる場合は、候補IDに対応するトークンを `proposalTokens` で返す。
- 既定は無効。本番の招待制デモは `TRIP_REVISION_ENABLED` と共通デモフラグが必要。
- 有効時はFirebase IDトークン、招待UID、Web App Check、共有利用枠が必要。[認証エラーと公開条件](API_ABUSE_PROTECTION.md)を参照。
- `PERSISTENCE_ENABLED` も有効な環境では、生成の前に本人報告の状態をTripへ記録することがある。この読み書きは生成と同じ操作の予約
  （Gemini・Places・Routesと保存の読み書き）に含め、書き込みは書き込み権で確定する。拒否・停止・利用枠超過のときはGemini・Mapsを呼ばない。

## 変更前後の移動区間の比較（`comparisons`）

`proposed`に、任意の`comparisons`を返す。**返したRevisionごとに高々1件**で、候補別の**一時的な比較データ**（保存しない）。

```ts
comparisons: {
  revisionId: string // 対応するRevision（tripId・baseTripVersion・targetStopIdは、そのRevisionが持つ）
  originalPlaceId?: string | null // 元施設の照合結果。null・旧応答で省略は未確認
  before: { fromPrevious: Slot; toNext: Slot } // 変更前：前の予定→対象、対象→次の予定
  after: { fromPrevious: Slot; toNext: Slot } // 変更後（候補）
}[]

Slot =
  | { presence: 'none'; reason: 'first_stop' | 'last_stop' } // 区間が存在しない（最初・最後の予定）
  | { presence: 'segment'; segment: TravelSegment } // 区間がある。known（判明済み）／unknown（確認できなかった）
```

- **区間が存在しない場合**（`none`）と、**区間はあるが、経路を確認できなかった場合**（`segment`の`unknown`）を区別する。
  `unknown`の理由は、`not_queried`（未照会・施設を特定できない）／`no_route`／`api_error`。公共交通は`transit_unsupported`。
- 数値は、**説明文（`Evidence.explanation`）から取り出さず、構造化された`TravelSegment`を使う**。
- **変更前の経路も、同じリクエストの中で測る**（元の施設を特定できれば`known`。できなければ`unknown`（`not_queried`））。
  UIは`originalPlaceId`が無い、候補と同じ、保存済みIDと不一致、または元施設の同定に本人報告の矛盾が残る場合、承認を止める。
- 契約で検証していること：比較は存在するRevisionに対して1件ずつ／変更前後で区間の有無が一致／区間の端点が、
  対象Stopと前後のStopに一致（変更前後でStop IDは維持される）。
- クライアントから戻された比較・`constraintCheck`・`evidence`は、承認の根拠として**信用しない**。適用の直前に再検証する。

## 処理の流れと判断

1. **候補の生成（Gemini、1回）**：対象1件だけの代替候補（名称と、短い理由）を最大3件。
   開始時刻・滞在時間・種別は、**変えない**（他の予定の時刻も、ずらさない）。AIは、Place ID・根拠・承認状態を決めない。
2. **候補の整理**：元の名称との完全一致・他の予定との名称重複・同名の候補を除く。元の施設と似た名称の別支店などは、Places照合に進める。
3. **前後の予定の特定（共有）**：前の予定・次の予定・元の予定のPlace IDを、**1回だけ**調べる（候補どうしで共有）。
   Place IDだけが必要なため、営業時間（Enterprise）は要求しない。
4. **変更前の移動を測る**：前→元、元→次を、構造化された区間として測る（候補どうしで共有）。
5. **候補ごとの照合**：Placesで施設を特定し、営業時間を確認する。施設を特定できない候補
   （候補なし・名称不一致・複数で絞れない）は、**実在を確認できないため、候補にしない**（Routesも呼ばない）。
   元の施設と同じPlace IDに解決した候補も除く。元の施設を特定できないときは、候補と別施設か確認できるまで承認できない。
   保存済みのPlace IDと照合結果が一致しない場合や、元の施設の同定に本人報告の矛盾がある場合も、元の施設は未同定として扱う。
   同じPlace IDの代替候補は一件にまとめ、異なるPlace IDの別支店は残す。前後の移動照会も候補のPlace IDごとに共有する。
6. **候補ごとの移動の検証**：**前の予定→候補**と**候補→次の予定**の、両方を測る。次の予定が固定予定でも、他の予定の時刻は
   動かさないため、「候補の終了＋移動時間 ≦ 次の予定の開始」で、固定予定への到達も判定できる。
7. **制約検証の結果（`constraintCheck`）**：
   | 状態        | 条件                                                                                                     |
   | ----------- | -------------------------------------------------------------------------------------------------------- |
   | `violated`  | 照合した営業時間に滞在が収まらない、時刻が重なる、または確認できた移動時間では間に合わない。候補から除く |
   | `satisfied` | 別施設であると確認でき、営業時間と前後の移動が情報源と整合し、承認に関係する矛盾が残っていない           |
   | `unknown`   | 施設の区別や制約を確認できない、または承認に関係する根拠に未解決の矛盾がある。候補として返し、承認は不可 |
8. **Revisionの組み立て**：`diff.before`は入力の予定、`diff.after`は候補（Place IDは、名称が一致した施設だけ）。
   根拠（`evidence`）は、`after`に付ける：施設の存在・営業時間・前の予定からの移動・**次の予定への移動**（`travel_time`）。
   `impactSummary`は、決定論的に組み立てる（AIの文章ではない）。

元の施設の休業報告は`diff.before`や現地報告の`context`に保持する。別施設の営業時間の根拠には使わない。
候補自身に付いた本人報告の矛盾や、適用範囲が不明な`other`の矛盾は、Places・Routesの整合で解消済みとしない。
`delayed`は通常の移動時間と元の時刻表だけで到着時刻を確認できない。`other`と旧形式の報告は影響範囲を確認できない。
`description`は本人の申告内容として保持する。判定には構造化された分類と対象を使う。
模擬情報は実際の照合の根拠に使わず、模擬報告のRevisionは適用できない。

## 移動手段（利用者が車を使えるとは限らない）

- **既定は徒歩だけ**で確認する。徒歩で間に合わない区間は、車で間に合っても、成立とは扱わない
  （車を使えるか分からないため。その場合、候補にならない）。
- **車は、利用者が使えると明示したとき**（`travelModes: ['walk', 'drive']`）だけ、徒歩で間に合わない区間に限って確認する。
  徒歩で間に合えば、車は調べない。返す区間の`mode`が、実際に使った手段（`walk`／`drive`）を示す。
- **公共交通は、現段階では未対応**（日本のRoutes APIで確認できない）。「徒歩（と車）では間に合わない」は、
  「公共交通なら間に合う」可能性を否定しない。説明文に「車・公共交通は、利用できるか分からないため、確認していません」等と明記する。
- 照合（`verifyTrip`、#7）も、同じ移動手段の制約を使う（既定は徒歩だけ。以前の「徒歩→車の自動切り替え」は廃止）。
- 利用者が、どの手段を使えるかを、画面でどう尋ねるか（設定・毎回の確認）は、UI側の判断。

## Maps APIの呼び出し回数

候補が**N件**のとき（徒歩だけの場合）：

| 呼び出し                                                  | 回数    |
| --------------------------------------------------------- | ------- |
| Places：前・次・元の施設（Place IDだけ。共有）            | 3       |
| Places：候補ごとの施設（営業時間を要求）                  | N       |
| Routes：変更前の2区間（共有）                             | 2       |
| Routes：候補ごとの前後の2区間（施設を特定できた候補だけ） | 最大 2N |

例：N=3なら、Places 6回・Routes 最大8回。車を使えると明示した場合は、徒歩で間に合わない区間だけ、追加で車を1回。
Geminiは1回。いずれも再試行しない。

## 失敗の区別

| 状況                                               | 応答                                                    |
| -------------------------------------------------- | ------------------------------------------------------- |
| Geminiの失敗                                       | `external_service_error`                                |
| 候補の施設検索が、すべて失敗                       | `external_service_error`（根拠を捏造しない）            |
| 元の施設の検索で通信に失敗                         | `external_service_error`                                |

## 適用時の再検証のための関数

承認・適用の処理が、**適用の直前**に、サーバー側で制約を再検証できるよう、
`checkRevisionConstraints(trip, revision, { maps, now, travelModes })`を公開している
（候補を旅程へ入れた状態で、営業時間・前後の移動を再検証し、`ConstraintCheck`と、根拠つきの`after`を返す）。

- 適用する側が、別に検証すること：**所有者の認可・Tripの版の一致・変更前のStopとの一致**。
- 再検証で得た結果（`constraintCheck`・`after`）を使って適用する。元の施設もPlacesで1回照合し直し、営業時間は要求しない。
  提案時の根拠は、候補に未解決の矛盾が残るかの確認に使う。成立の根拠はPlaces・Routesから再取得する。
- 適用側は提案時の`context`を含むRevisionを渡す。文脈が欠ける、形式が不正、対象が異なる、または模擬報告の場合は照会前に拒否する。
- `satisfied`以外（`not_possible`・`unknown`・`external_service_error`）は、適用しない。
- 候補を作ったときの `travelModes` を候補保存時に引き継ぎ、適用の再検証に使う。生成・保存とも省略時は徒歩だけ。

### 候補の来歴と適用契約

短命のHMAC署名を採用する。候補IDに対応する署名を、候補・元の移動手段と一緒に既存の保存APIへ渡す。
署名にはUID、旅程の保存項目（版を含む）、対象・候補ID、候補の保存項目、理由、報告文脈、移動手段、判定に必要な本人報告を含める。
本人が報告した内容の事実性は別に扱う。サーバーで全候補を生成直後に保存する方式なら改変を防げるが、
比較だけの利用にもFirestoreの書き込み・保存枠管理・期限切れ候補の削除が必要になる。
署名方式では、15分の期限とサーバー間で共有する秘密鍵を管理する。

既存UIの依頼理由と報告文脈の一致検証は維持する。適用の応答と再取得、本人報告の保存範囲は
[保存済みRevisionの適用契約](FIRESTORE_PERSISTENCE.md#revisionの適用と再取得)を参照。
PR #50の現地フローを接続する際は、報告の `category` と `targetStopId` を渡し、比較の `originalPlaceId` を検証する。
模擬報告では専用の適用不可理由を表示する。説明文の先頭で分類する暫定判定は、構造化報告と共通判定へ切り替える。
生成・保存・UIで、理由と希望条件を結合した入力を1000文字以内とする。適用コールバックには候補の署名が必須。
報告の確認・解消を接続し、`revision_endpoints_changed` と `revision_report_changed` では最新状態で候補比較からやり直す。
確定後に更新された旅程を表示する場合は、確定時の施設と版に基づく表示を引き継がない。

### #29の予約量

統合済み。課金APIと保存の共通の操作枠（`runCostlyOperation`）を通す。数値は `src/server/cost-control/costs.ts` の予約量。

| 経路                                                    | Gemini | Places | Routes | Firestore読取 / 書込 |
| ------------------------------------------------------- | -----: | -----: | -----: | -------------------: |
| `POST /api/trips/revise`（保存無効）                    |      1 |      6 |     16 |                0 / 0 |
| `POST /api/trips/revise`（`PERSISTENCE_ENABLED`有効）   |      1 |      6 |     16 |               70 / 5 |
| `POST /api/trips/{tripId}/revisions/{revisionId}/apply` |      0 |      4 |      4 |              14 / 10 |
| `POST /api/trips/{tripId}/revisions`                    |      0 |      0 |      0 |             140 / 15 |
| `GET /api/trips/{tripId}/revision-reports/{stopId}`     |      0 |      0 |      0 |               14 / 0 |
| `POST /api/trips/{tripId}/revision-reports/{stopId}`    |      0 |      0 |      0 |               70 / 5 |

生成時は元・前後の3施設と候補最大3施設を調べる。Routesは元の前後2区間と候補3件の前後6区間を、最大2手段で調べる。
適用時は元・前後・採用候補の4施設を調べ、採用候補の前後2区間を最大2手段で調べる。元施設には営業時間を要求しない。
有料と保存を同時に使う2経路（保存有効の生成、適用）は、1つの操作で有料枠と保存枠の両方を予約する。UID別の同時枠も両方を消費し、
どちらかの上限に達すれば、Gemini・Maps・業務DBのいずれも呼ばずに429／503で拒否する。
有料の呼び出しは予約量を超えると送信前に遮断される（計量済みclient）。適用の有料照会は、同じ操作の予約内の計量済みclientだけを通す。

適用の読取14・書込10は暫定の保守枠。実際は、事前の2読取、確定取引の2読取・2書込（再試行しない）、結果不明のときの確定結果照会の2読取に収まる。
業務の取引（本人報告の記録、候補の保存、本人報告の解消、適用の確定）は、すべて操作の書き込み権（`operation.write`）で確定し、
リースの失効・回収や期間切替の後に古い書き込みが確定しない。取引は1操作につき1回だけで、コールバックは再試行しない。
再送の確認に使う個別のTrip・Revision GETは既存の保護を使う。
生成・保存・報告操作には旧文書からの報告復元も予約する。保存は、基本読取3件（親Trip・既存候補・保存枠カウンター）に、復元対象の
上限超過検出を含む13件と保存枠確認最大12件を加えた28読取と、候補・カウンター・Tripの3書込を5倍で予約する。
生成と報告解消は、上限超過検出用の1件も含めて14読取・1書込を5倍で予約する。
課金保護の接続時は、書き込み開始前に残り時間を確認する。コミットを始めた後の失敗やタイムアウトは、
適用では同じ操作の読取枠内で版と承認状態を一度だけ照会し、確認できなければ `apply_result_unknown` として扱う。

## 現地報告フローの暫定ガード（#46で共通判定に置き換える）

現地報告からの再計画（`src/features/onsite-flow/`）は、候補を表示する前に、**承認可否を下げる方向にだけ**働く暫定のガード
（`onsite-approval-guard.ts`）を通す。**共通の根拠・制約判定（#46）の代わりではなく、#46が共通判定を直したら置き換える暫定の処理**。
ガードは候補を成立（`satisfied`）へ引き上げず、もとの判定より承認に近づけない。サーバー側の適用の再検証には作用しない（クライアントの表示と承認ボタンのみ）。

| 条件                                                                                                   | 下げる先                                          |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| (a) 候補のPlace IDが、報告の対象になった予定（休業と報告された施設）のPlace IDと同じ（名称が違っても） | `violated`（承認不可）                            |
| (b) 候補の根拠に、`user_report`由来の`conflicting`が残っている                                         | `violated`（他の根拠が整合していても承認不可）    |
| (c) 遅れの報告の後は、元の時刻表だけを根拠にした「間に合う見込み」を使わない                           | `unknown`（現在の状況を評価できないため承認不可） |

- 契約（`RevisionContext`）には、報告の種類（休業・遅れ）の欄が無く、`report.kind`は`actual`／`simulated`だけ。
  種類は、報告フォームが作る説明文（プリセットの文言＋任意の補足）の形から読み取る。読み取れない説明文（「その他」の自由記述）は、(a)(b)だけが対象。
- (a)は、休業以外の報告でも、同じ施設を代わりの候補にしない（理由の文言だけが変わる）。
- Place IDが未同定（`null`）どうしは、同じ施設とは扱わない。
- 理由は`constraintCheck.explanation`に入れ、比較欄と承認欄に表示する。
- 模擬報告（`simulated`）にも同じ基準を使う。模擬報告の適用禁止（承認が`apply`へ届かない）は別の防御。
