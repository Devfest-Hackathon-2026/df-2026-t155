# GroundTrip：設計原則と技術境界（暫定）

> **以下の基本思想は優先するが、具体的なUIレイアウト・配色・画面数やMVPの詳細を確定仕様と見なさない。UXの原則・未決定事項は [`UX_DESIGN_PRINCIPLES.md`](UX_DESIGN_PRINCIPLES.md) に整理する。** 新しいチーム合意・Issueの受け入れ条件を優先する。

## プロダクトの核

**AIの提案を、人間が根拠で選ぶ（Own the Why）。** 旅行者にAIのミス探しを強いるのではなく、旅程の一部を便利に修正する操作の中で、事実・未確認・制約・選択理由を確認できるようにする。

- 旅行前：Geminiが候補を生成し、Places/Routesのデータと制約を照合する。
- 旅行前・現地：指定した**1地点の部分修正**を共通の処理で行い、固定予定や予約を守る。根拠・未確認・前後差分を提示し、本人が採否を決定する。
- 旅行後：体験と変更理由から得た学びを、**本人が編集・承認したものだけ**保存する。
- 次回：保存した好み・制約を利用し、反映された変更を説明できるようにする。
- デモでは架空の現地トラブルを「模擬報告」と明記し、実測/照合データと混同しない。

## 重要な不変条件

1. **生成と検証は別責務**。Geminiの文章を正しさの証拠にしない。Places/Routesの結果も未来の営業・実地の状況を保証しない。
2. 検証結果は少なくとも**情報源と整合／矛盾あり／確認できない**の3種類を区別し、取得時刻・根拠・対象の不確実性を扱う。「整合」は正しさの保証ではない。
3. 修正対象のStop IDと固定予定を明示し、**未承認では既存旅程を変更しない**。固定時刻・移動時間・滞在時間を再検証し、不可能な変更は成立案として提示しない。
4. 「候補なし」「情報不足」「外部API失敗」を区別する。失敗時にAIの推測で根拠を埋めたり、黙って固定予定を変更したりしない。
5. 本人が承認した学びだけ次回へ適用する。基盤モデルの追加学習を行ったかのように説明しない。
6. ユーザー単位の認可、入力とLLM出力のスキーマ検証、サーバー側の秘密管理・API費用制限を重視する。Firebase Admin SDKなどサーバー権限を使う箇所はFirestore Rulesに依存せず**サーバーでアクセス制御**する。
7. Google Maps Platformデータのキャッシュ・保存・表示規約を守る。Place IDと施設詳細の保存可否を区別する。

## 実装境界（厳密なフォルダ構造ではなく責務の案）

- **画面**：旅行条件入力、旅程カード、候補比較、根拠・不確実性の表示、本人の承認。固定予定・変更差分・重要な未確認事項を把握できるUIを優先する。画面数・配色・レイアウトは未確定。具体的なUX上の確認事項は `UX_DESIGN_PRINCIPLES.md` を参照する。
- **Next.js API層**：認証確認、入力チェック、エラーレスポンス、外部サービス呼び出しの調整。秘密鍵をブラウザへ渡さない。
- **アプリケーション／ドメイン層**：変更案の生成調整、固定予定・移動時間の決定論的な制約検証、差分計算、承認・保存の状態遷移。HTTPやReactから独立してテスト可能にする。
- **外部サービス層**：Gemini/Places/Routes/Firestoreを個別のアダプターで扱い、失敗や未確認を明示する。
- **共有契約**：Trip、Stop、Evidence、Revision、Learningなどの必要最小限のモデルとAPI入出力を定義。Zodでランタイム検証し、型をフロント/サーバーで共用する。

MVPの目安は**日帰り1地域・3〜4地点・1地点の部分修正**。最初から複数日最適化・GPS常時追跡・高度な個別AI学習を作らない。

## 最低限の検証シナリオ

- 固定した14時の予定を保ちながら、12時の昼食だけ変更できる。
- 移動時間などで固定予定が守れない候補は警告し、不可能な案を自動確定しない。
- 情報が不足した場所、臨時休業未確認、Places/Routes失敗を「未確認」等として扱う。
- 承認前の旅程・学びは保存済みの確定情報を上書きしない。
- API障害時にも既存データを安全に保持する。
