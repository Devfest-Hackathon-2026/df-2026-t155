# GroundTrip Git / GitHub運用方針

## 1. ブランチとマージ

- `main`を基準に、作業ごとに短命のブランチを作成する（GitHub Flow）。長期運用する`develop`ブランチは作らない。
- ブランチ名は**英語・小文字・ハイフン区切り**とする。Issue番号は原則付けない。
  - 例：`feat/itinerary-generation`、`fix/opening-hours`、`chore/firebase-setup`
- **`main`への直接pushは禁止**（リポジトリ初期化時を除く）。小さな変更もPRを経由する。
- マージ方式は**Squash mergeのみ**。マージ後は作業ブランチを削除する。
- PRは小さく保ち、動く状態の変更をこまめに`main`へ取り込む。
- **APIキーなどの秘密情報は絶対にcommitしない。**

## 2. コミットメッセージ

**Conventional Commits形式**を使用する。Type・Scopeは英語、変更概要は日本語。本文は原則書かず、変更理由・検証内容はPR本文に記載する。

```
<type>(<scope>): <変更概要>
<type>: <変更概要> # スコープなしの場合
```

- **Scopeは任意**。変更の主な機能・責務を1つに特定できる場合に付ける。複数領域にまたがる場合やリポジトリ全体の変更では省略する。
- 主なScope：`plan`（旅程）、`verify`（検証）、`feedback`（振り返り）、`learning`（学習）、`auth`（認証）、`ui`（共通UI）、`data`（データ層）。必要に応じて追加してよいが、同じ領域で表記を揺らさない。

| Type       | 用途                     |
| ---------- | ------------------------ |
| `feat`     | 機能追加                 |
| `fix`      | 不具合修正               |
| `refactor` | 動作を変えないコード整理 |
| `perf`     | 性能改善                 |
| `test`     | テストのみの変更         |
| `docs`     | ドキュメントのみの変更   |
| `build`    | 依存関係・ビルド設定     |
| `ci`       | CI/CD設定                |
| `chore`    | その他の保守作業         |

例：`feat(verify): 営業時間の検証機能を追加`、`ci: PRの自動チェックを追加`

取り消しには必要に応じて`revert`を使用する（注意して使用）。

## 3. Pull Request(PR)・レビュー

- **PRタイトルもコミットと同じ形式**（Type・Scopeは英語、概要は日本語）にする。PR本文には**変更内容・理由・確認結果**を日本語で簡潔に記載する。`.github/pull_request_template.md`に準拠する。
- PR作成時、**1コミットならそのコミットメッセージがタイトルに自動入力されることがある**。複数コミットの場合はPR全体を表すタイトルに**手動で整える**。いずれも作成前にConventional Commits形式になっているか必ず確認する。
- マージはGitHub上でPRを経由して行う。ローカルなどでマージしたりはしない。
- Squash後のコミットタイトルもPRタイトルに合わせる（基本的には自動でそうなるので問題ないが、マージ画面で一応確認する）。
- **機能追加・バグ修正・コード変更・認証／DB／デプロイ設定の変更は、原則として、他のメンバー1名からApprove（承認）を得てからマージする。**
- **誤字修正やドキュメントのみなど、明らかに低リスクな変更はレビューなしのセルフマージ可**。ただしPR作成とCI成功は省略しない。

## 4. Issue・CI/CD

- **主要機能・独立したタスク・重要なバグ**はIssueを作成し、担当者と完了条件を明確にする。誤字やPR内で完結する軽微な修正はIssue不要。
- Issueタイトルは通常の日本語でよい。Issue番号はPR本文で関連付ける。
  - 完全に対応したら`Closes #12`、関連付けのみなら`Refs #12`。
- PRは**CI成功後にマージ**する。CIではlint・型チェック・テスト・ビルドを確認する。
- `main`へのマージは公開環境への反映につながるため、動作確認済みの変更だけをマージする。デモ前のデプロイ停止・手動切替はチーム内で共有する。
