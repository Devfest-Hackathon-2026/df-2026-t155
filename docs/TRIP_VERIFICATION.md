# 旅程の照合（Places・Routes）

生成した旅程の各予定を、Google Maps Platform（Places・Routes）の情報と照合し、根拠（`Evidence`）を付ける。
AIの提案、外部情報による照合、決定論的な制約チェック、本人の承認は、別の責務として扱う。
ここで行うのは、照合だけ。予定の内容（名称・時刻・滞在・固定）と旅程の版は、変えない。

## API

`POST /api/trips/verify`（`TRIP_VERIFICATION_ENABLED=true` のときだけ有効。既定は無効で、503）

- リクエスト：`{ trip }`（旅程1件）。それ以外の項目（移動手段の指定`travelModes`など）は、無視せず、`400 invalid_request`で拒否する。
- 応答：`200 { status: 'verified', trip }`（根拠とPlace IDを付けた旅程）、`502 external_service_error`（Placesを実際に呼んだ全予定で、Mapsの呼び出しが失敗。呼んだ予定が0件なら、失敗とせず`verified`）。
- `400 invalid_request`：形式の不正、または、予定の時刻が重なっている・時刻順でない旅程（Mapsは呼ばない）。この時刻の検証は、ハンドラーの事前チェックに加え、内部の`verifyTrip`でも行う（`invalid_trip`として返し、ハンドラーが400に対応づける。防御の二重化）。
- 課金を伴うため、認証・利用制限が入るまでは、機能フラグで停止する。

### 移動手段

**このAPIは、徒歩だけで移動を確認する**（車を使えるとは限らないため）。公共交通は、MVPでは照会の対象外。
内部の`verifyTrip`は、`travelModes`で車を明示的に許可できるが、公開APIには出していない。
必要になったときに、リクエストの検証から照合処理までを接続する。

## 乗車・乗換は照合しない

`kind: 'transport'`（乗車・乗換）の予定は、施設ではないため、Placesを呼ばない（呼び出し回数にも数えない）。Place IDは`null`、根拠（`evidence`）は**空**にする（実際に照会していない情報を、確認結果として扱わない）。隣接する移動区間も、Place IDがないため、Routesを呼ばず、根拠を付けない。

## 施設の同定（`place_identity`）

次の条件をすべて満たす候補だけを、同じ施設として採用する。満たさなければ「確認できない」で、Place IDも付けない。

- 名称が、完全に一致する（部分一致は採用しない）。比較で無視するのは、空白と、引用符・括弧類（「」『』【】“”）の装飾だけ。「/」「・」などの記号は、名称の一部として扱う（「A/B」と「AB」は別）。
- 括弧書きは、支店・別館などの識別情報として、位置も含めて一致が必要（「資料館（別館）」と「資料館」、「A（店）B」と「AB（店）」は別）。
- 候補の所在地が、旅程の地域と、**住所の行政区画の階層**で一致する。住所の先頭から、都道府県 → 郡（→ 町・村）／市（→ 区）／（東京都は）特別区、の順に読み取る（町・村は、郡の下にあるものだけ。「神田神保町」のような町名は、行政区画として読み取らない）。地域は、要素に分け（「福島・郡山」なら「福島」「郡山」。「京都市東山」のように続けた要素は、京都市→東山区の階層として読む）、**すべての要素を、同じ住所の、重ならない行政区画で確認できたときだけ**、一致とする。住所に文字列として含まれるだけでは、一致としない（東京都目黒区東山を「京都・東山」としない。大阪市福島区や、福島県までしか分からない住所を「福島・郡山」としない）。住所が無い、日本の住所として読み取れない、階層が不明確、地域の要素が行政区画でない（駅名・町名など）場合は、採用しない。
- 同名の候補が複数（異なるPlace ID）ある場合は、1つに絞らない。

地域の書き方：要素の区切りは、「・」「,」「、」「/」空白に加え、ハイフン類（`-`・`–`・`—`・`−`）と波線（`〜`・`~`）。語尾の「周辺・付近・近辺・エリア・地区・方面・一帯」と「市内・県内・府内・都内・区内・町内・村内」は、重なっていても外す（「京都市内」→京都市、「東京都内」→東京都、「京都・東山エリア周辺」→京都・東山）。駅名・温泉地（「京都駅周辺」「箱根温泉」）は行政区画でないため、従来どおり一致しない（意図した制限）。

Placesの検索語は「予定の名称 + 地域」。地域は、括弧書き（全角・半角。「（架空デモ）」など）を除いたものを使う（除いて空なら、元の地域）。

Place IDは、採用した施設だけに付ける。誤ったPlace IDが、営業時間・移動の根拠に伝わらない。

## 営業時間（`opening_hours`）

- 判定できるのは、通常営業時間の範囲内かどうかだけ。臨時休業・特別営業・混雑は、判定できない。
- 営業時間のデータが欠落・空配列・解釈できない区間を含むときは、営業とも休みとも断定せず、「確認できない」とする。確認できた区間に収まる場合だけ、「整合」とする。開店と閉店が同じ曜日・時刻の区間は、丸1週間の営業とも解釈できないため、不完全なデータとして扱う。週をまたぐ営業は、閉店が開店より小さい場合だけ。
- 24時間営業は、日曜0:00開店・閉店なしの、ちょうど1件だけの場合に限る。
- 営業時間は施設の現地時刻で表される。旅程のタイムゾーンが日本標準時のときだけ照合する（それ以外は「確認できない」）。`Asia/Tokyo`の別名（`Japan`など）も日本として扱う（`Intl`で正規化して判定）。営業時間（最上位の課金区分）は、この日本の旅程のときだけPlacesに要求する。採用する施設は、住所を日本の行政区画として読み取れたものだけなので、施設の現地時刻は日本標準時と同じ。住所に「Japan」の文字があるかどうかでは、判定しない。

## 移動（`travel_time`）

- 前の予定の終了から次の予定の開始までに、徒歩で間に合うかを、Routesで確認する（呼び出しは、区間ごとに最大1回）。
- **「矛盾あり（間に合わない）」と言えるのは、使える手段のすべてを確認できて、どれでも間に合わないときだけ。** 一部の手段を確認できず、確認できた手段では間に合わない場合は、区間全体を「確認できない」とする（確認できた所要時間は、内部の結果に保持する）。確認できなかった手段と、その理由は、対応させる。
- 施設を特定できない区間は、Routesを呼ばず、**Routes由来の根拠を付けない**（出典と照合日時を付けた、確認結果として扱わない）。施設を特定できないことは、施設の存在の根拠で示す。
- 根拠の説明には、Places由来の値（名称・営業時間）を載せない。移動は、計画上の余裕から導いた結果（「余裕◯分」「◯分不足」）だけを載せる。

## 保存と表示

- 保存してよいのは、Place IDだけ。名称・住所・営業時間・所要時間は、処理中にのみ使う。
- 画面（トップ画面の「根拠を確認する」）は、**このアプリの照合API（`POST /api/trips/verify`）を、1操作につき1回だけ**呼ぶ。
  これは、サーバーが**Googleの外部APIを1回だけ呼ぶ**という意味ではない。サーバーは、予定の数に応じて、Placesを予定ごとに1回
  （乗車・乗換は除く）、Routesを区間ごとに最大1回、合計で複数回呼ぶ（`verifyTrip` の `calls` が実際の回数）。
  課金や利用制限は、画面の呼び出し回数ではなく、外部APIの呼び出し回数で考える。
  Google由来の根拠を表示する領域には、帰属表示と枠を付けている（`docs/GOOGLE_MAPS_COMPLIANCE.md`、Issue #34）。

### 画面からの呼び出しの保護（Issue #29）

- **クライアントの二重送信防止（実行中の再押下を受け付けない）は、課金の利用制限の代わりにならない。** 画面を経由しない呼び出し、
  複数の端末・タブからの呼び出しは、止められない。認証と利用制限は、サーバー側で行う（#29）。
- 認証ヘッダーを付ける場所は、`browser-verify.ts` の1か所。`createBrowserVerifier({ getHeaders, requireAuth })` で、画面の `verify` に渡す。
  - `requireAuth: false`（既定・現状）：トークンを取得できなくても、ヘッダーなしで送る。サーバーに認証がまだ無いため。
  - `requireAuth: true`：トークンを取得できなければ**送信せず**失敗する（fail-closed）。失敗の種類は `auth_required`
    （認証基盤のエラー〈`ClientAuthError`〉は、その文言のまま伝える。通信の中断とは区別する）。
- サーバーが返す認証・利用制限のエラーは、本文の形に関わらず、ステータスで判定し、**結果を採用しない**。
  `401`・`403` は `unauthorized`（認証が必要、または失効）、`429` は `rate_limited`（利用制限）。画面の文言も区別する。
- **`TRIP_VERIFICATION_ENABLED` は、認証・利用制限・予算の上限（#29）が完成するまで、有効にしない。**

### 旅程が変わったときの根拠の扱い

照合の最中・後に旅程が変わったときの扱いは、変わったものによって分ける（`merge-verification.ts`、`withdraw-verification.ts`、`verifiable-trip.tsx`）。

- **固定の切り替えだけ**：固定は根拠（存在・営業・移動）に影響しない（承認・予約とも独立）。照合結果を取り下げず、確認中の通信も中止しない。
  確認中に切り替えた固定は、結果の到着後も残る。結果からは根拠（Place IDと証拠）だけを取り込む
  （サーバーは固定の切り替えを知らないため、結果の固定で上書きしない）。
- **内容が変わった**（名称・時刻・滞在・種別・順序の変更。部分修正の適用など）：「現在の予定に対して有効な根拠だけ」を残す。
  変更前の旅程と変更後の旅程を比べ、Places・Routes由来の根拠とPlace IDを、次のとおり扱う。**「照合前の状態」へは戻さない**
  （再照合で「確認できない」になった結果を、古い「整合」で上書きしないため）。
  - 変更で新しく付いた根拠（部分修正の候補の根拠）：残す。
  - 変更前から引き継がれた根拠：述べている範囲が変更前と同一のときだけ残す。それ以外は取り下げ、未確認に戻す。
    - 施設の存在・営業時間：その予定の名称・種別・開始・滞在（と旅程の日付・地域・タイムゾーン）とPlace IDが同一。Place IDが変わる、または`null`になる場合、引き継がれた`place_identity`・`opening_hours`は取り下げる。
    - 前の予定→この予定の移動：この予定と前の予定の両方が同一（ID・内容・Place ID）で、前の予定が隣のまま。
    - この予定→次の予定の移動：この予定と次の予定の両方が同一で、次の予定が隣のまま。
    - 何についての根拠か特定できないもの：この予定と前後の予定のすべてが同一。
  - 引き継がれたPlace IDは、その予定の内容が同一のときだけ残す。新しく付いたPlace IDは、古いもので上書きしない。
  - Place ID変更後に新しく取得したPlaces根拠と、公式情報・本人報告・模擬データ由来の根拠は保持する。新旧根拠を識別できない同一スナップショットは、Place ID変更時に引き継ぎとみなして取り下げる（安全側に倒す）。
  - 公式情報・本人の報告・模擬データ由来の根拠は、照合の結果ではないので、そのまま残す。再照合でも、置き換えない。
  - 確認中だった場合は、通信を中止して結果を採用せず、中止した理由（「照合中に旅程の内容が変わりました。最新の内容で照合し直してください。」）を
    `role="alert"` で出す。この通知は、次に「根拠を確認する」を押すまで残す。
  - 取り下げた根拠があるときの画面の状態は、「変更後の一部は未確認」（影響を受けない予定の根拠が残っている）、または
    「変更後は未確認」（照合の根拠が残っていない）。
- どの場合も、固定予定の名称・時刻・固定を照合結果で書き換えない（応答の同一性は `api-client` で検証し、書き換えられた応答は採用しない）。

### 移動の根拠の方向（区間）

移動の根拠（`travel_time`）は、区間の終点側の予定に付く。契約（`Evidence`）には、どの区間かを表す項目が無いため、
サーバーが作る根拠のidの命名規約で、方向を決める（`src/features/trip-map/evidence-scope.ts` が、この規約を読む唯一の場所）。

| id                              | 区間                | 作るのは             |
| ------------------------------- | ------------------- | -------------------- |
| `evidence-{予定id}-travel`      | 前の予定 → この予定 | 照合、部分修正の候補 |
| `evidence-{予定id}-travel-next` | この予定 → 次の予定 | 部分修正の候補       |

- 区間（A→B）の根拠は、Bの `-travel` と、Aの `-travel-next` のうち、Routes由来のものだけ。**B→CをA→Bとして扱わない。**
  路線図の区間ラベルと、詳細シートの「前の地点から」は、同じ判定（`segmentEvidence`）に従う。
- 規約に合わない移動の根拠は、区間を特定できないものとして、「情報源と整合」などの判定に使わない（未確認として扱う）。
- 規約とサーバーの実際の出力の一致は、`evidence-scope.test.ts` の契約のテスト（実際の `verifyTrip`・`reviseTrip` の出力）で確かめる。
  **idの命名規約は、契約ではなく実装上の取り決めである。** 契約に区間の端（前後の予定のIDなど）を持たせる変更は、別のIssueで行う。

### 画面の通知

結果（未確認・確認中・照合結果あり・変更後の一部は未確認）は `role="status"` で状態の1文だけを読み上げ、件数の内訳と確認した範囲は読み上げの外に置く。
失敗と中止は `role="alert"` で、結果の通知とは別の要素に出す。

- 概要の件数は、Places・Routesで照合した「根拠」の件数（施設の存在・営業時間・移動の確認項目ごと）で、予定の数ではない。
  公式情報・本人の報告・模擬データ由来の根拠は、この件数に含めず、「ほかに◯件（Google Mapsでの照合の結果ではありません）」と別に示す。
- 照合した項目と、照合していない項目（未確認）、照合日時を、項目ごとに区別して示す。
- 外部の情報源に1件も照会しなかったとき（乗車・乗換だけの旅程など）は、「照合しましたが、外部の情報源に照会した項目はありません」とし、
  施設・営業時間・徒歩移動を確認したようには表示しない。
- 成功済みの照合結果が表示されている状態で再照合が失敗したときは、「表示中の根拠は、以前の照合結果です（照合日時）。今回の確認は反映していません」と伝える。
  表示している照合の根拠が無いときだけ、「根拠は未確認のまま」と伝える。
- 照合は、旅程の確定・予約・保存を意味しない。
- 「整合」は、確認できた情報と一致したという意味で、現実の正しさを保証するものではない。
