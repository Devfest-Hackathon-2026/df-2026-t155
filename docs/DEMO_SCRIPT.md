## 1. ねらい

**審査員に伝える一言**

> AIの旅程は、もっともらしいけれど、根拠が見えず、現地で崩れます。GroundTripは、AIの提案を、根拠と一緒に見せて、直すのは1地点だけ、決めるのは本人、という流れにしました。

見せたいこと（優先順）：

1. AIが作った旅程は**提案**であり、確認済みの事実ではないこと（**未照合**と明示される）。

3. 直すのは**選んだ1地点だけ**で、固定予定と、承認前の旅程は変わらないこと。
4. 学びは**本人が承認したものだけ**で、AIの再学習ではないこと。

### 5分版（オンライン用）に伸ばす場合の差分

4分版に、次の約1分を足します。

- 導入に +15秒：課題を、旅行中に崩れる具体例（閉店・遅れ）で話す。

## 2. 事前準備

### 2.1 環境

1. Node.js 24.15以上の24系とpnpmを用意し、`pnpm install --frozen-lockfile` を実行する。
2. `.env.example` を `.env.local` にコピーする。値・鍵・トークンはコミットしない。
3. ローカルの、意図して限定した検証環境でのみ、接続を確認したいAPIの機能フラグを `true` にする。既定では `false` で503を返す。

   - `GOOGLE_CLOUD_PROJECT`、`GOOGLE_CLOUD_LOCATION`（既定 `global`）、`GEMINI_MODEL`（既定 `gemini-3.5-flash`）：Gemini/Vertex AI。
   - `TRIP_GENERATION_ENABLED`：旅程生成。
   - `TRIP_VERIFICATION_ENABLED`：Places・Routes照合（通常画面の「根拠を確認する」から接続）。
   - `TRIP_REVISION_ENABLED`：部分修正候補（通常画面の現地報告から接続）。
   - `TRIP_REVISION_APPLY_ENABLED`：本人承認後の適用。`PERSISTENCE_ENABLED`とサーバー専用の`REVISION_PROPOSAL_SIGNING_KEY`も必要。秘密鍵の実値は資料・画面・Gitに含めない。
   - `LEARNING_CANDIDATES_ENABLED`：学び候補作成。
   - `PERSISTENCE_ENABLED`：Firestore本人別保存（保存・振り返り・学び選択に接続。BearerとApp Checkが必須）。

4. Gemini/Places/Routesのサーバー接続はADC。ローカルでは `gcloud auth application-default login` を使う。Firebase Auth/Firestoreの検証は、まずJava 21以上を用いて `pnpm emulators` で行う（`docs/AUTHENTICATION.md`・`docs/FIRESTORE_PERSISTENCE.md`）。
5. `pnpm dev` を起動し、`http://localhost:3000` を開く。トップの通し導線（生成→照合→保存→現地報告→振り返り）と、`/demo`・`/reflection?demo=1`のモック動作を確認する。
6. **有料APIや保存APIを、認証・総量制限のない公開URLで有効化しない**。#29の対策・本番IAM/ADC/Rules・Cloud Billingの設定を完了してから公開判断する。

## 3. 手順（4分版）

**この時間配分は下書きです。** 画面接続・実API・本番設定はまだ検証しきれていません。できない機能を架空の動作で補って「実装済み」と紹介しないでください。

### 0:00〜0:25　導入（社会課題）

- 操作：トップ画面を開いておく。
- 説明：「AIが作る旅程は自然に見えても、施設の営業や移動の根拠は別に確認する必要があります。GroundTripは、提案・照合・制約チェック・本人承認を分け、旅の一部だけ安全に変えることを目指しています。」

### 0:25〜1:10　旅程を作る（技術活用）[main・画面接続あり／ローカル検証時のみAPI有効化]

- トップで「京都・東山」、将来の日付、希望を入力。固定予定「14:00から60分」を追加し、「旅程を作成する」。
- Geminiが作るのは**未照合の提案**。生成された路線図で、予定を選ぶ詳細シートと固定の切り替えを見せる。固定予定の入力・生成結果の保持を確認する。
- 画面上で固定を切り替えてもFirestoreには保存されません。「旅行条件・保存済みの旅程」から入力へ戻れます。再生成に失敗したときは「旅程へ戻る」で直前の旅程を確認できます。
- 入力欄の下に「前の旅の学びを使う」があります。保存済みの承認済み学びがあれば選べ、**選んだ学びのIDと版だけ**をサーバーへ送ります（サーバーが本人の保存済みデータで照合する。選んだ後に学びが変わっていれば409で選び直しを案内）。学びを使って作った旅程は、現時点では保存できません。
- 本番でフラグが無効なら503になるため、その場合は`/demo`（架空旅程）に切り替え、生成したふりをしません。

### 1:10〜1:45　根拠の照合（技術活用）[画面接続あり／ローカル検証時のみAPI有効化]

- 生成後の「根拠を確認する」を押したときだけ、`POST /api/trips/verify`を1回呼ぶ（施設同定・通常営業時間と徒歩移動、#27）。実際のPlaces/Routesの結果を出典・照合日時つきで実演する。営業時間・経路は当日の保証ではありません。
- 旅程が変わる操作（現地報告からの部分修正の適用）をすると、前回の照合結果のうち影響を受けた根拠は取り下げられ、「変更後は未確認」に戻る。照合を勝手にやり直さない。
- APIが無効・未設定なら、`/demo`を開き、**「これはデモ用の架空の根拠で、実API照合ではありません」**と明示する。未照合と照合して確認不能だった状態を区別して説明する。

### 1:45〜2:40　1地点の部分修正（完成度）[コード接続済み／実環境確認が必要]

- `/demo`で昼食の「この予定だけ変更」を選ぶ。理由を入力し、架空の候補を切り替え、路線図の青い分岐・元の灰色の経路・前後差分と固定予定への影響を見せる。
- 通常画面で実APIの候補を示す場合は、旅程を保存し、路線図の予定を開いて「この予定だけ変更」を選びます。旅行前の修正理由・希望条件を入力して候補を比べます。現地で実際に問題が起きた場合は、次の現地報告の導線を使います。
- 保存済みの旅程では、本人の承認後に候補を保存し、サーバーが再検証して適用します。実演では保存・適用のフラグと認証・利用枠が有効な環境で、対象だけが変わり固定予定が残ることを先に確認します。`/demo`の架空候補は実保存しません。
- デモで条件成立としている候補も模擬結果。未確認を無条件に承認可能と扱わず、変更前の旅程を維持する。

### 2:40〜3:10　現地報告と再計画（完成度）[コード接続済み／実環境確認が必要]

- 保存した旅程で「旅行中」に切り替えます。手動で現在の予定を進め、現地の報告を始めます（#41・#42）。
- 「閉店・臨時休業」「混んでいる」「遅れそう」などを報告し、候補の比較（`POST /api/trips/revise`、フラグ有効時）まで進める。模擬報告は「デモ用の想定」と明示し、候補を比べられても旅程には適用されない。
- 実際の報告では、候補の比較と本人承認後の適用を示せます。適用結果が不明なときは再操作を止め、対象候補の承認記録と最新旅程で確認します。実環境で動作確認できるまでは実演可能と扱いません。

### 3:10〜3:45　振り返りと学びの承認（完成度）[画面接続あり／保存APIの有効化が必要]

- 旅程を保存（「本人の操作で旅程を保存する」。`PERSISTENCE_ENABLED`と匿名認証が必要）して「保存した旅行を振り返る」を押すと、振り返り画面で保存した旅程が選ばれます。「旅程へ戻る」で照合結果を引き続き確認できます。
- 感想を入力して、Geminiの学び候補（1〜3件）を編集・承認・却下し、承認したものを保存する。編集した候補は再承認が必要。基盤モデルの再学習を行ったと説明しない。
- 実際の旅程を使わず、架空の旅程で見せたい場合は`/reflection?demo=1`（保存はしない）。`/reflection`（パラメータなし）は本人の保存済み旅程。

### 3:45〜4:00　次回旅行とまとめ（ピッチ）[画面接続あり／保存APIの有効化が必要]

- 「旅程へ戻る」から「旅行条件・保存済みの旅程」を開く。保存した学びは、入力画面の「前の旅の学びを使う」に現れる（保存直後に一覧を読み込み直す）。選んで新しい旅程を作ると、選んだ学びのIDと版だけが送られ、サーバーが本人の保存済みデータと照合して使う。結果が学びによる変更かどうかは、生成結果だけでは断定しない。
- 学びを使って作った旅程は、適用記録の再検証が未接続のため**保存できない**（画面にその旨が出る）。連続して実演する場合は、学びを使った旅程を保存せずに見せる。
- まとめ：「GroundTripはAIの提案を、人間が根拠で選ぶことを目指します。完成している操作と、今後接続する部分を明確に区別しています。」

**補足**：実際に完了した接続が増えた場合は、上記の[未接続]や[デモ用の想定]を本番実機の結果に合わせて更新し、4分間を計測し直してください。

## 4. 見せない・見せられないもの

**未接続の機能は実演しない。模擬データを実測と称さない。**

- **照合の実環境での確認**：画面接続は済んでいるが、Places/Routesの実疎通と公開設定は実環境で確認できた範囲だけを実演する。`/demo`の根拠は架空。
- **路線図上の部分修正**：トップの路線図の「この予定だけ変更」は未接続（現地報告の導線が候補生成の入口）。`/demo`の候補は架空。
- **変更の確定・保存**：保存済み旅程から本人承認後に適用APIを呼ぶ。サーバーの確定結果を確認できた場合だけ適用済みと説明する。
- **旅行中の再計画の確定**：実際の報告から候補比較・適用まで接続。模擬報告は比較までで、実環境で確認できた操作だけ実演する。
- **学びの保存と次回反映の実環境での確認**：画面は接続済み（保存→次の生成で選択→サーバーで照合）。保存API・Firebase・App Checkを有効にした環境での通し確認は、まだ。学びを使って作った旅程は保存できない。
- **Google Maps帰属**：帰属表示部品・`/terms`はmainに存在するが、実際にGoogle由来の情報を画面に表示する箇所では帰属・利用条件を適切に結び付ける必要がある。
- **公共交通／当日の保証**：公共交通のRoutes照会はMVP対象外。臨時休業・実際の混雑・遅延は保証しない。
- **公開保護**：Bearer・招待UID・App Check・利用枠はコードに接続済み。Issue #29の本番設定・実環境疎通・監視と停止の確認は未完了で、本番の安全な公開が完了したとは説明しない。

## 5. フォールバック

### 5.1 外部API・設定の失敗

- **Gemini 502／通信中断**：入力値は保持されます。限定的に再試行し、失敗したら`/demo`へ切り替えます。「`/demo`は事前に用意した架空データ」と明言する。以前の生成結果の表示は、再生成失敗時に保持されません。
- **機能フラグがfalse（503）**：`.env.local`の設定を、ローカルの検証環境でのみ確認します。本番で安全対策なしにtrueへ変えません。
- **照合API・部分修正APIの失敗**：これらのルートはmainにあります。接続後に502や確認不能などの実際の画面挙動を検証します。現時点の`/demo`は本番API失敗時の自動切替機能ではありません。
- **候補が作れない／情報不足**：条件を変更し、候補なしと外部サービス失敗を区別して表示します。作れなかった候補をAIの推測で補わない。
- **保存APIの503／401／409**：`PERSISTENCE_ENABLED`、Bearer IDトークン、期待版などを確認する。保存に失敗した内容を「保存済み」と表示しない。
- **課金上限・クォータ超過**：専用の自動停止・説明画面はまだ未実装（#29）。Cloud Consoleのクォータと停止手順を事前に確認し、模擬データの`/demo`に切り替える。

### 5.2 デモの保険

- `/demo`：**架空の**路線図・根拠・候補比較を、Gemini・Places・Routesを呼ばずに操作できます。承認した候補の実保存は行いません。
- `/reflection?demo=1`：**架空の**Tripで、感想から学び候補を作るUIを確認できます。候補作成APIが無効なら生成はできません。この画面では保存せず、次の旅にも反映されません。
- 事前に実行して成功した画面の動画を使うなら「**事前に収録した実行結果**」と明示し、現在のライブ操作と取り違えさせない。
- 現時点で、実APIの応答を再生する自動デモモードや、課金上限での自動停止機能はありません。

## 6. 想定される質問と答え

### なぜ、AIの提案をそのまま使わないのですか。

AIの旅程は、もっともらしい一方で、施設の実在・営業時間・移動時間の正しさを保証しません。GroundTripは、Geminiの文章を正しさの証拠にしません。提案、照合、制約チェック、本人の承認を分け、最後は本人が根拠を見て選びます。AIのミス探しを利用者に強いるのではなく、旅程の一部を直す操作の中で、根拠を確認できるようにしています。

### 「情報源と整合」とは何ですか。正しいということですか。

いいえ。**取得した時点の情報源と、矛盾しなかった**という意味です。現実の正しさ、将来の営業、当日の混雑は保証しません。根拠は、「情報源と整合」「矛盾あり」「確認できない」の3つに分け、出典・照合日時・対象日時を示します。まだ照合していないものは、「確認できない」ではなく**未照合**と表示します。

### 固定予定は、どう守っているのですか。

- 生成では入力した固定予定の名前・時刻・滞在時間を優先して保持します。
- 固定したStopは、部分修正の対象として選べません。候補API（#28）は1地点だけの差分と、固定時刻・前後の徒歩移動の条件を判定します。
- 承認後はサーバーでも固定予定・版・根拠・制約を再確認して適用します。通信が切れた場合は、結果を確認できるまで再操作を止めます。実環境の通し検証は別途必要です。

### 学びは、何が保存されますか。

- 学びの候補生成と本人の編集・承認・却下UIはmainにあります。次の旅へ適用するのは、本人が承認した学びだけです。
- 本人ごとにLearningを保存・取得・撤回するFirestore API（#44）もmainにあります。
- トップ画面で旅程を保存して振り返ると、承認した学びは保存APIへ保存され、次に旅程を作るときに選べます（`PERSISTENCE_ENABLED`が必要）。`/reflection?demo=1`の架空デモは保存しません。AIモデルの追加学習ではありません。
- 学びを使って作った旅程は、適用記録をサーバーで再検証する仕組みが未接続のため、保存できません。

### Googleのデータは、保存していますか。

Firestoreの保存DTOで残す外部Mapsデータは**Place IDのみ**。Placesの表示名・住所・座標・営業時間・Routesの所要時間は保存対象から除外します。再取得したTripの根拠は未照合に戻り、必要なら再照合します。Places・Routesの照合は、生成後の「根拠を確認する」から呼べます。帰属表示部品と`/terms`は#40でmainに追加済みです。

### 路線図は、地図ですか。

いいえ。訪問順を示す**模式図**で、実際の位置関係や縮尺は表していません。

### 公共交通は、扱えますか。

MVPでは、照会の対象外です。公共交通を使う案は、移動時間を「確認できない」とし、AIの推定で埋めません。Routes APIで、`TRANSIT` の実測が4回とも空だったことが理由です（`docs/API_CONNECTIVITY_FINDINGS.md`）。

### 臨時休業や渋滞は、考慮されますか。

いいえ。営業時間は通常営業時間だけで、渋滞や遅延は見ていません。そのため、「整合」を保証として扱いません。

### いま実際に動いているのは、どこまでですか。

READMEの「主な特徴と状態」を参照してください。コード上では生成→照合→保存→現地報告からの候補比較・本人承認後の適用→振り返りと学び保存→次の生成での学び選択を接続しています。**学びを使った旅程の保存は未対応**です。公開URLの有料APIは既定で無効で、実環境の通し確認も必要です。

### 位置情報や個人情報は、集めていますか。

このコードは位置情報を取得しません。入力した旅行先・希望・固定予定・感想は、生成のためにサーバーからGeminiへ送ります。秘密の認証情報はクライアントに渡しません。画面からのBearer・App Check送信と、本人別の保存APIを接続しています。匿名認証は一人一アカウントや身元を保証しません。提出用のデモUIDは共有であり、個人情報は入力しません。

### 課金は、どう制御していますか。

課金を伴う4つのAPIは機能フラグで既定無効です。Firestore保存APIも既定無効です。認証・利用者別／全体の制限、予算・クォータ・停止手順（Issue #29）の整備前に、一般公開で有効にしません。
