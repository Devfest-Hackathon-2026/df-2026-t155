# 振り返りと承認済みの学び（Issue #12・保存に依存しない部分）

旅行後の振り返りから「学び」の候補を作り、本人が編集・承認したものだけを、次回の旅程づくりへ渡す。
学びの保存はパーソナライズであり、Gemini自体の再学習ではない。共通契約は`docs/DOMAIN_CONTRACTS.md`の`Learning`。

## 構成

| 場所                                          | 責務                                                                           |
| --------------------------------------------- | ------------------------------------------------------------------------------ |
| `src/lib/learnings/lifecycle.ts`              | 編集・承認・却下・次回に渡せる学びの選択（純粋ロジック。画面とサーバーで共用） |
| `src/server/learnings/generate-candidates.ts` | 振り返りの材料から、Geminiで学びの候補（1〜3件）を作る                         |
| `src/server/learnings/store.ts`               | 承認済みの学びの保存先（インターフェースとメモリ実装）                         |
| `src/server/learnings/handler.ts` ほか        | `POST /api/learnings/candidates`（候補の作成だけ。承認・保存はしない）         |

## 守っていること

- 候補はすべて**未承認（pending）**で返す。AIは承認状態・ID・適用地域を決めない（地域は旅程の地域をサーバーが入れる）。
- 編集した学びは、承認済みでも**必ずpendingに戻し、再承認を求める**。
- 次回に渡せるのは、**承認済みで、適用範囲（全地域／同じ地域）が合うものだけ**。各要素を契約（`ApprovedLearning`）で形式を検証し直す。
- 保存できるのは**承認済みだけ**。利用者ごとに分離する。
- 情報源との不一致（`verification`）と、個人の好み（`preference`）を区別する。
- **模擬報告（デモ用の想定）は、実際に起きた出来事として学びにしない。** AIへの指示だけに頼らず、アプリケーション側で除外する。
  材料判定とプロンプト生成は、共通の`usableRevisions`（**承認済みで、模擬報告ではない変更**）だけを使い、模擬報告はAIへ渡さない。
  感想が無く、使える変更も無ければ、AIを呼ばず情報不足とする。
- 材料（感想か、使える変更）が無ければ、AIを呼ばず情報不足とする。未承認・却下の変更も、材料にしない。
- 感想・変更理由は、指示ではなくデータとしてAIに渡す。

## API：POST /api/learnings/candidates

- リクエスト：`{ trip, revisions, feedback }`（`revisions`は同じ旅程の変更履歴、`feedback`は1000文字以内、本文は64KB以下）。
- 成功：HTTP 200、`{ status: 'proposed', learnings }`（1〜3件、すべてpending）。
- 失敗：`no_candidates`／`insufficient_information`は422、`external_service_error`は502。API層のエラーは400／413／415／500／503（旅程生成APIと同じ）。
- 既定は無効。本番の招待制デモは `LEARNING_CANDIDATES_ENABLED` と共通デモフラグが必要。
- 有効時はFirebase IDトークン、招待UID、Web App Check、共有利用枠が必要。[認証エラーと公開条件](API_ABUSE_PROTECTION.md)を参照。
- Geminiの呼び出しは1リクエスト1回。再試行しない。

## 承認済みデータとの接続

#10の[保存API](FIRESTORE_PERSISTENCE.md)が、本人確認、元Tripの所有権、専用操作によるLearning承認と撤回を扱う。
保存済みの学びを再編集する間は、旧版を有効なまま保持する。専用APIで新版の承認が成功した時点で置き換わる。

候補生成APIの `revisions` は現在もクライアント申告。振り返りの接続では、本人の保存済みTripと
適用履歴をサーバーで取得する。現行の確認画面はローカル状態で承認・却下を扱うため、
専用の承認APIを接続する際に、承認済みの版と編集下書きを分けて扱う。

## 次回の旅への学びの接続契約（#13）

画面で見た内容と違う学びが、黙って生成に使われないようにする（Own the Why）。選択は内容ではなく、
**画面に表示したときの版**と、**それを取得した認証セッション**に紐づける。

| 場所                                                           | 責務                                                                                                                                               |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/features/learning-reuse/api-client.ts`                    | 本人の承認済みの学びを、取得したセッション（`SessionScope`）と組（`ScopedValue`）で取得する。要求はUID・世代一致時だけ送信し、応答採用前にも再確認 |
| `src/features/learning-reuse/learning-list.ts`                 | 取得スキーマの本文上限の検証と、表示してよい一覧かの判定（重複ID・上限超過）                                                                       |
| `src/features/learning-reuse/learning-reuse-picker.tsx`        | 版つきで表示し、選択を `ScopedValue<{ id, version }[]>` で通知する。UID・認証世代・地域が変わったら一覧・選択・読み込みを捨てる                    |
| `src/features/learning-reuse/selection-scope.ts`               | `resolveSelectionForRequest`。生成リクエストの直前に、選択時と現在のUID・認証世代が同じことを確認して選択を取り出す唯一の口                        |
| `src/server/learning-reuse/selection.ts`                       | `resolveSelectedLearnings`。選択を本人の保存済みデータと照合して、採用する学び（検証時点のスナップショット）を確定する                             |
| `src/features/learning-reuse/learning-application-summary.tsx` | 生成後の適用記録（学びID・対象の予定・AIの説明）の表示                                                                                             |

### 選択の契約

- 選択IDは `{ id, version }`（`LearningSelectionSchema`）。本文・承認状態・所有者は運ばない。
  `version` は `GET /api/learnings` が返す版（`VersionedLearning.version`）で、再承認のたびに加算される。
  **IDだけの選択（`string[]`）や、版のない選択は受け付けない**（サーバーは `invalid_selection`、取り出し口は `InvalidLearningSelectionError`）。
- サーバーは `resolveSelectedLearnings(store, ownerUid, region, selections)` で、版つきの一覧
  （`FirestoreLearningStore.listVersionedApproved`）を取得し直して照合する。`ownerUid` は検証済みActorのUIDだけを渡す。
  版を返せないストア実装は渡せない（型で拒否。返った値が版つきの承認済みでなければ実行時にも拒否する）。
  地域だけで本人の全件を取り出す `getApplicableLearnings` は、選択の根拠にしない（版も選択も持たないため）。
- 版が現行と違えば、内容が同じでも `selection_changed` とする（再承認で内容が差し替わった可能性を区別できないため。
  保守側に倒す）。撤回後に同じIDで保存し直しても、過去に発行した版は再利用しない。
- 出力は、選択順の `ApprovedLearning[]`。本文は `MAX_LEARNING_CONTENT_LENGTH`（120文字）を再検証し、超える場合は採用しない。
  `ApprovedLearningSchema` は既存文書の読み取り互換のため上限を持たない。
- 空の選択は「学びを使わない」と解釈し、保存先を読まずに `[]` を返す。
- 地域は前後の空白を除いた**完全一致**（`normalizeLearningRegion`。画面とサーバーで同じ関数を使う）。
  全角・半角などの表記揺れの正規化は未決定（`DOMAIN_CONTRACTS.md`）のため、画面に「同じ表記の地域だけ」と明示する。

### 選択を認証セッションに結び付ける（画面側）

サーバーは**トークンのUIDで**学びを引く。同じ `{ id, version }` でも、UIDが違えば本文が違うことがある
（AとBの双方に `learning-x` の版1があり、本文だけ違う場合）。Aが見て選んだ選択をBのトークンで送ると、
Aが見ていないBの本文が、黙って採用される。これを防ぐため、画面は
[認証のセッションスコープ](AUTHENTICATION.md)（`SessionScope` / `ScopedValue` / `useSessionScope`）と同じ方式で、
一覧と選択を取得時のセッションに結び付ける。独自のセッション管理は持たない。

- 親は `useSessionScope()` の状態をそのまま `LearningReusePicker` の `session` に渡す。
  Pickerは `loadApprovedLearningOptions({ scope })` で取得し、一覧を `ScopedValue<VersionedLearning[]>` で保持する。
  取得のトークンは `getAuthHeadersForScope(scope)` で作る。UIDまたは認証世代が変わっていればトークンを出さず、`session_changed` で失敗する。
- 選択は `ScopedValue<{ id, version }[]>`（`ScopedLearningSelection`）を含む `LearningReuseSelection` で親へ通知する。
  「どの認証セッションの利用者が、画面で見たどの版を選んだか」の対応を型で残し、結果画面に表示する本文も保持する。
- UID・認証世代（`scopeEpoch`）・地域が変わったとき、再読み込みしたとき、認証の復元中・失効・エラーのとき、
  Pickerがアンマウントされるときは、進行中の読み込みを `AbortController` で中止し、
  **親へ `null`（選択なし）を通知して**親が持つ古い選択を無効にする。
  選択を解除したことは、画面の状況表示（`role="status"`）で利用者に伝える。
- 取得を始めたセッションと違うセッションの一覧が返ってきたときは、その一覧を採用しない。
  中断後に届いた古い応答は、状態にも反映しない。UIDと認証世代が同じなら（通常のトークン更新などの再通知）読み直さず、選択も保つ。
- 生成リクエストを送る直前は、必ず `resolveSelectionForRequest(selected, currentScope)` を通す。
  選択時のセッションと現在のUIDまたは認証世代が違えば `SessionChangedError`（選択を空にして続行しない）。
  送信側のトークンも `getAuthHeadersForScope(scope)` で作る。現在のUIDだけを見た `getAuthHeaders()` を作り直して使わない。

```ts
const scope = await captureSessionScope()
const selections = resolveSelectionForRequest(selected, scope) // 違えば SessionChangedError
const headers = await getAuthHeadersForScope(scope) // 送信側のトークンも同じ認証世代
```

画面側の保護はUXの安全網であり、所有者の分離はサーバー側（`ownerUid` で引く）が担う。

### 取得・表示・採用の境界を揃える

| 境界                         | 検証                                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 保存層（書き込み・読み取り） | 本文120文字。読み取りで上限を超える文書は不正として除外し、`listInfo.skippedInvalid` で知らせる（一覧は不完全）  |
| クライアント取得（Zod）      | `ReusableLearningListResponseSchema`。契約の形式に加え、本文120文字以内。1件でも超えれば一覧ごと不完全として扱う |
| 表示の入口（Picker）         | `isSelectableLearningList`。上限超過・ID重複を含む一覧は表示せず、読み込み関数が差し替えられても同じ判定を通す   |
| サーバー採用（resolver）     | `isLearningContentReusable`。選んだ学びの本文が上限を超える場合は採用しない（`unavailable`）                     |

上限判定は `isLearningContentReusable`（`MAX_LEARNING_CONTENT_LENGTH`）の1関数に統一する。

不完全な一覧・認証失効・地域変更・古い応答の扱い。いずれも、空の一覧とは区別して示し、学びを使わずに旅程を作る道を残す。

| 状況                                                                     | 画面の扱い                                                                                                 |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 打ち切り・破損による除外・件数の不一致・ID重複・上限超過                 | 一覧ごと使わない（`incomplete`）。再読み込みを案内する                                                     |
| 401・403・認証の復元失敗・セッション終了                                 | 読み込みを始めない、または失敗にする。再読み込みでは直らない状況は案内を出さない。匿名アカウントは作らない |
| 取得前または応答採用前にUID・認証世代が変わっていた（`session_changed`） | 要求前は送信せず、応答後は一覧を採用せず失敗にする。再読み込みを案内する                                   |
| 地域が変わった                                                           | 選択を解除し、新しい地域で読み直す。解除したことを伝える                                                   |
| 中断後・別条件で届いた応答                                               | 採用しない                                                                                                 |

### エラーとHTTP状態

保存先の例外（破損文書による `invalid_stored_data`、`storage_unavailable` など）は、内部情報を含めず
`unavailable` に変換する。統合側には `LearningSelectionError` だけが届く。

| `LearningSelectionError.code` | HTTP | 起きるとき                                                            | 利用者への案内                             |
| ----------------------------- | ---- | --------------------------------------------------------------------- | ------------------------------------------ |
| `invalid_selection`           | 400  | 選択の形式が不正、重複ID、上限（40件）超過、所有者・地域が空          | 入力を見直す                               |
| `selection_changed`           | 409  | 版の不一致、撤回、他人のID、存在しないID、適用地域の不一致            | 最新の一覧を取得して、選び直す             |
| `unavailable`                 | 503  | 一覧を取得・検証できない（破損・障害・版なし）、本文が120文字を超える | 学びを使わずに旅程を作る、または時間をおく |

認証・失効は、これらより前に `requireActor` が401で扱う。

### 生成時点の契約（検証時点のスナップショット）

`resolveSelectedLearnings` が返した `ApprovedLearning[]` は、**Firestoreを読んだ時点（T1）の、本人の承認済み・現行版・
地域一致・上限以内の学び**である。生成はこの値（検証時点のスナップショット）だけを使う。
外部のGemini呼び出し全体をFirestoreトランザクションで囲む設計は採らない（外部呼び出しの間、
読み取りや書き込みの競合を持ち続けられない）。その代わり、確認を次のように分ける。

| 時点 | 出来事                                        | 学びの扱い                                                                                               |
| ---- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| T0   | 画面が一覧を取得・表示し、利用者が選ぶ        | `{ id, version }` を取得時のセッションと組で保持する。本文・承認状態は信用の根拠にしない                 |
| T1   | 生成Routeが `resolveSelectedLearnings` を呼ぶ | **ここで承認状態・所有者・版・地域・本文上限を確認する**。返った値が、この生成の検証済みスナップショット |
| T2   | Geminiの呼び出し中（数秒以上）                | 学びは更新・撤回されうる。再確認しない。スナップショットで続行してよい                                   |
| T3   | 生成Routeが旅程を組み立てて返す               | 結果は「検証時点のスナップショットで作った提案」。承認済みであり続けている証明ではない                   |
| T4   | 利用者が旅程を保存する                        | 保存処理が、適用記録の学びの所有者・承認状態・版を保存トランザクション内で再検証する（提案、下記）       |
| T5   | 保存後・後日                                  | 保存済みの適用記録は履歴。撤回・更新されても書き換えない。表示は「現在の内容」と区別する                 |

**撤回・更新が起きた時点ごとの扱い**

| 起きた時点                 | 生成                                     | 結果と利用者への案内                                                                                                 |
| -------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| T0〜T1（選択後、検証前）   | 生成しない（409 `selection_changed`）    | 一覧を取得し直して選び直しを求める。選択を黙って外して続行しない                                                     |
| T1〜T3（検証後、Gemini中） | 検証時点のスナップショットで続行してよい | 結果に、検証した `{ learningId, version }` を記録する（提案）。保存時に再検証される                                  |
| T3〜T4（生成後、保存前）   | 生成済み                                 | 保存時の再検証で拒否する（提案）。「学びが撤回または変更されたため保存できません」と示し、選び直して再生成を案内する |
| T4より後                   | —                                        | 保存済みの旅程は変更しない。適用記録は残し、学びの内容は「内容を取得できません」と示す                               |

**責務分担**

| 担当                       | 責務                                                                                                                                                                                       | 責務ではないこと                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| 画面（Picker・取り出し口） | 取得時のセッションに結び付けて一覧・選択を持つ。送信直前に現在のセッションと照合する                                                                                                       | 承認状態の判断。サーバーの所有者検証の代替       |
| 生成Route（#54）           | 認証（`requireActor`）。`resolveSelectedLearnings` を1回呼び、検証済みの学びだけをGeminiへ渡す。適用記録を検証済みの学びIDに限る。409と503を区別して返す。結果に検証した版を添える（提案） | Gemini呼び出し中の再確認。学びの撤回・更新の反映 |
| resolver                   | 所有者・版・地域・本文上限・一覧の完全性を1回の読み取りで確認し、スナップショットを返す。副作用なし                                                                                        | 保存。生成後の再確認                             |
| 保存処理（旅程の保存API）  | 保存トランザクション内で、適用記録の各学びについて所有者・承認状態（撤回されていない）・版（記録した版と現行が一致）を再検証する（提案）。満たさなければ保存しない                         | 生成時の選択の判断                               |

**混同しないこと**

- 「生成時点の承認確認」は、T1でその版が本人の承認済みだったという確認だけである。結果が出たことは、
  学びが今も承認済みであることを意味しない。
- 「保存の可否」は、T4の再検証で決める。撤回・更新された学びを根拠にする適用記録つきの旅程は、新たに保存しない。
- 「再利用の可否」は、撤回・更新された学びを次の生成で選べないことである（Pickerは現行の承認済みだけを表示し、
  resolverは現行の版だけを採用する）。保存済みの旅程の履歴とは別。

**提案（未実装。保存形式とAPI契約を変えるため、実装前に共有する）**

1. `LearningApplication` に検証した版（例 `learningVersion`）を加える。
   影響範囲：共通Trip契約（`DOMAIN_CONTRACTS.md`）、Tripの保存DTO（Firestoreの保存構造）、生成の組み立て（`assemble.ts`）、
   適用記録の表示。代替案：(a) Trip契約は変えず、生成の応答に別の欄（例 `verifiedLearnings: [{ id, version }]`）を添え、
   保存APIの入力にも同じ欄を設ける（保存形式は不変だが、API契約が増え、履歴に版が残らない）。
   (b) 版を記録せず、保存時は現行の承認の存在だけを確認する（内容が差し替わったことを検出できない）。
   **推奨は1**（根拠にした版が履歴に残り、「現在の内容」との差を示せる）。
2. 旅程の保存APIが適用記録つきの旅程を受け付ける（現在の `CreateTripBodySchema` は `learningApplications` を空に限る）ようにし、
   保存トランザクション内で `users/{uid}/learnings/{id}` を読んで、所有者・承認状態・版を再検証する。
   不一致は 409 `learning_changed` とする（生成時の `selection_changed` と区別する）。
3. 生成Routeは、結果に検証した `{ id, version }` を添える。画面はそれを保存リクエストへそのまま渡す。

### 生成APIとの接続（統合ブランチで実施済み）

- 旧 `POST /api/trips/generate` は、承認済みの学びの本文そのもの（`learnings`）を、認証なしの本文（最大32KB）から信用して受け取っていた。
  **この経路は閉じた。** 選択肢のうち「2. 既存ルートに選択の欄を追加し、本文由来の `learnings` は受け付けない」を採った。
  - HTTP契約は `GenerateTripHttpRequestSchema`（`src/server/trip-generation/http-request.ts`）。旅行条件に加え、
    `learningSelections: { id, version }[]`（最大40件・ID重複なし）だけを持つ。`strictObject` なので、旧形式の `learnings` が付いた本文は **400 `invalid_request`**。
  - 内部の `GenerateTripRequest`（`learnings` を持つ）は、サーバーが `resolveSelectedLearnings` で確定した学びから組み立てる。HTTPの本文としては受け付けない。
    HTTPで再構築しないため、解決された学びの大きさが32KB制限の影響を受けない。
  - 学びの選択があるときだけ、費用の予約に `COSTS.generateWithLearnings`（Gemini 1・業務Firestore読取 `LEARNING_LIMIT + 1`）を使う。空選択は `COSTS.generate`（Geminiのみ）。
- 応答：選択の不一致は **409 `selection_changed`**、保存済みの学びを確認できない場合は **503 `learnings_unavailable`**。
  後者は機能停止の `service_unavailable`（503）とはstatus文字列で区別する。
  画面（`TripPlanner` / `HomePlanner`）は、409では学びの一覧を取得し直して選び直しを求め、
  503（`learnings_unavailable`）では「学びの選択を外して旅程を作る」を案内する。選択を黙って外して生成を続けない。
- 画面の送信側（`requestTripGeneration`）は、選択を選んだ時点の認証セッションと組（`ScopedLearningSelection`）で受け取り、
  送信の直前に `resolveSelectionForRequest` で現在のセッションと照合する。違えば送らず `session_changed` で失敗する。
  ヘッダーも `getProtectedApiHeadersForScope(scope)` で作り、通信を `beginSessionScopeOperation` に登録して、応答の採用前にも再確認する。
  本文は既知の項目だけで組み立て、呼び出し側が余分な項目（旧 `learnings` など）を渡しても載せない。
- 生成後のTripの `learningApplications` を保存する際は、参照した学びの存在・所有者・現行の版を、
  保存トランザクション内で検証する（上記の提案、および[保存API](FIRESTORE_PERSISTENCE.md)の#13の項）。

**#54で必ず対応する統合条件（1〜4・6は実装済み。5もHTTPの再構築をやめたことで解消。画面側の接続はトップ画面 `HomePlanner`）**

1. Pickerで選んだ `{ id, version }` を、親・APIクライアント・生成Route経由でresolverへ渡す（IDだけの選択へ戻さない）。
2. UID・認証世代・地域が変わったとき、親に保持した古い選択も無効にする（`scopeEpoch` / `scope.uid` の変化、`onSelectionChange(null)`）。
   送信の直前に `resolveSelectionForRequest` を通す。
3. 既存の `POST /api/trips/generate` から、クライアントが申告した学びの本文を承認済みとして信用する経路を閉じる。
4. 認証・検証済みの学びだけをGeminiへ渡す。
5. 検証済みの内部データを、HTTPリクエストとして再構築することで生じる不要なサイズ制限（32KB）を解消する。
6. `409`（選び直し）と `503`（学びを使わずに作る）を区別し、利用者の選択を黙って変更しない。

### 適用記録の表示

- 生成結果画面では、送信時の選択に対応する本文を、旅程の `learningApplications`（学びID・対象Stop・説明）と組にして表示する。
  本文はPickerがその版で表示した内容を使用する。APIに送信する選択は `{ id, version }` で、旅程には本文を保存しない。
- 適用先を記録した学びは生成時の対象予定と「AIによる説明（未検証）」を表示する。
  生成条件に渡しても反映先が報告されなかった学びは、別に一覧表示する。
- 生成結果同士の差分は提示しない。同じ条件で生成結果が変わる可能性があり、学びによる変化かどうかは確認できない。
- 適用記録がある旅程はプレビューで確認できる。保存は上記の再検証が接続されるまで制限する。
